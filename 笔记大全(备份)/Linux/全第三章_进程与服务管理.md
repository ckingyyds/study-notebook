## 1. 进程基本介绍（必会）
> 🏷️ ⭐ 开发必会 —— 软件开发日常高频使用，务必掌握

### 1.1 什么是进程（了解）
> 🏷️ 了解即可 —— 开发知道概念就行，不用深记
- **进程（Process）** 是程序的一次执行过程。
- 你电脑硬盘上存着一个 `python app.py` 代码文件，**躺在磁盘里不动的时候，它只是【程序（文件）】**。 当你敲命令 `python app.py`，系统把这个程序加载到内存、分配资源、开始运行，**这个正在活着、正在运行的东西，就叫【进程】**
- 程序是静态的（磁盘上的可执行文件），进程是动态的（内存中的执行实例）
- 进程是操作系统**分配资源**的基本单位（内存、文件描述符、CPU 时间）
- **线程（Thread）** 是 CPU 调度的基本单位，同一进程的线程共享内存空间
- 一个进程至少包含 1 个线程（主线程），多线程进程如 MySQL、Nginx worker

#### 1.1.1 程序 vs 进程（关键区别）

| 对比项 | 程序（Program） | 进程（Process） |
|--------|----------------|-----------------|
| 存在形式 | 磁盘上的二进制文件 | 内存中的执行实例 |
| 生命周期 | 永久存在 | 有创建、运行、消亡 |
| 资源占用 | 仅占磁盘空间 | 占用 CPU/内存/文件描述符 |
| 数量关系 | 1 个程序可对应多个进程 | 1 个进程对应 1 个程序 |
| 例子 | /usr/sbin/sshd | `ps -ef \| grep sshd` 看到的多个 sshd 进程 |

> 💡 开发岗只需理解到这一层：**程序是文件，进程是运行起来的实例**。一次启动一个程序 = 创建一个进程，启动多次 = 多个进程。后面所有命令（ps、kill、top）都在操作进程。

### 1.2 进程类型（必会）
> 🏷️ ⭐ 开发必会 —— 软件开发日常高频使用，务必掌握

按启动方式分三类：
- **交互进程**：你在终端敲命令启动的（如 `vim`、`top`），关掉终端就没了
- **批处理进程**：cron 定时任务触发的脚本，不和用户交互
- **守护进程（Daemon）**：后台常驻的服务进程，名字通常以 `d` 结尾——`sshd`（SSH 服务）、`crond`（定时任务）、`mysqld`（MySQL）、`systemd`（系统 1 号进程）

#### 1.2.1 怎么让自己的程序后台常驻（开发常用）

##### 先说清楚这节要解决什么问题

> **场景：** 你 SSH 连上服务器，跑了个程序（比如 Django/Flask），它占着终端，浏览器也能访问。然后你**合上笔记本盖子 / 关掉 SSH 窗口**，过一会儿重连 —— **程序没了，页面打不开了**。
>
> 这一节就带你**亲手复现这个问题，再用 nohup 解决它**。全程照抄命令就能做，不需要自己准备任何代码。

**"合上笔记本盖子"是关机吗？** 不是，是笔记本进入**睡眠**（Windows 叫"睡眠"，macOS 叫"合盖睡眠"）。

| 笔记本状态 | 电源 | 网络 | SSH 连接 |
|------------|------|------|----------|
| 开机运行 | 通 | 通 | **保持连接** ✅ |
| **合盖睡眠** | 弱电维持内存 | **网卡断电** | **连接断开** ❌ |
| 关机 | 断 | 断 | 连接断开 |

合盖子 → 笔记本网卡断电 → SSH 通道中断 → 服务器发现"客户端不见了" → SSH 会话结束。**笔记本没死，只是网络断了**，但对服务器来说效果一样：会话没了，里面跑的程序也被带走了。

##### 实际开发中，到底哪些场景需要后台常驻？（必会）

> 你可能想："我的服务器在云端，我不合笔记本盖子，不就没事了？" 其实**不是**。合盖子只是最容易理解的"触发 SSH 断开"的方式，实际开发中触发断开的场景多得多。

**核心问题：SSH 会话 = 前台程序的命根子，会话一断程序就死。** 只要 SSH 会话可能在程序运行期间结束，你就需要后台常驻。

**真实开发场景清单**：

| 场景 | 为什么 SSH 会断 / 为什么需要后台 | 典型例子 |
|------|-------------------------------|---------|
| **1. 本地电脑关机/重启** | 你每天下班关电脑，SSH 会话随之关闭，但后端服务要 7×24 小时跑着 | Django/Flask/Node 后端、Java 服务 |
| **2. 本地网络断开** | WiFi 不稳、切网络（公司网 → 手机热点）、VPN 掉线，SSH 立刻断 | 在家办公网络抖动 |
| **3. 长时间运行的任务** | 任务要跑几小时甚至几天，你不可能一直开着 SSH 窗口等 | 数据爬取、数据导入/导出、模型训练、批量发邮件 |
| **4. 多窗口操作冲突** | 前台跑着服务就占住了这个窗口，你想在同一台机器上做别的事就得再开一个窗口；后台跑可以释放窗口 | 一个窗口跑 Django，另一个窗口改代码/查日志 |
| **5. 服务器在云端，你本地断电** | 笔记本没电关机、Windows 自动更新强制重启，云端的程序不能跟着死 | 云服务器部署的任何服务 |
| **6. 跳板机/堡垒机超时** | 公司跳板机有会话超时（比如 30 分钟无操作自动断开），前台程序跟着死 | 国企/大厂运维环境 |
| **7. 临时调试不想被打扰** | 前台跑程序时误按 Ctrl+C 就停了，后台跑更安全 | 测试环境临时起个服务验证 |

**一句话总结**：**只要这个程序的生命周期 > 你这次 SSH 会话的预期时长，就必须让它后台常驻。** 后端服务、定时任务、长耗时脚本，全部都需要。

下面的**第 0～5 步就是"方法一：nohup"的完整实操**（装环境 → 前台跑 → 看它死 → nohup 救活 → 验证 → 善后）。建议按顺序在自己服务器上做一遍，做完再看后面的方法二（生产环境用 systemd）。

###### 第 0 步：装好 python3（环境准备，只需做一次）

CentOS 7.6 **默认只有 Python 2，没有 python3 命令**。先检查：

```bash
python3 --version
```

- 显示 `Python 3.6.8` 之类版本号 → 已经装了，直接跳到第 1 步；
- 显示 `bash: python3: 未找到命令` → 没装，继续下面：

```bash
sudo yum install -y python3
```

> ⚠️ 如果这条命令报 `Could not resolve host: mirrorlist.centos.org`，是 CentOS 7 源失效了，先按**本章 7.1.0 节**把 yum 源换成阿里云 vault，换完再回来执行安装。

装完再验证一次：

```bash
python3 --version
# Python 3.6.8        ← 看到版本号就 OK（3.6 自带 http.server，够用）
```

> 💡 为什么下面用 `python3 -m http.server 8080` 做实验？它是 Python **自带的临时网页服务器**，不用写一行代码、不用装任何库，敲一条命令就能跑，专门用来演示"前台/后台/断开"。真实开发时把它换成你的 Django、Flask、Java、Node 程序即可。

###### 第 1 步：以前台方式跑起来（感受"终端被占住"）

**开第 1 个 SSH 窗口**（用你的终端工具连上服务器，用户名/IP 换成你自己的）：

```bash
ssh lwc@你的服务器IP
cd ~                              # 先进家目录（http.server 会共享"当前目录"）
python3 -m http.server 8080
# Serving HTTP on 0.0.0.0 port 8080 ...     ← 看到这行 = 启动成功
```

**另开第 2 个 SSH 窗口**（再连一次同一台服务器），验证服务能访问：

```bash
curl http://localhost:8080
# 返回一大段 HTML（Directory listing ...）= 服务正常 ✅
```

回到第 1 个窗口，按 `Ctrl + C` 先把它停掉（为第 2 步做准备），回到命令提示符。

###### 第 2 步：证明"SSH 一断开，前台程序就死"

在**第 1 个窗口**重新前台启动：

```bash
cd ~
python3 -m http.server 8080     #`-m`：`module`，把后面的模块**当做脚本直接运行**
```

然后**模拟 SSH 断开**（任选一种）：

- 命令行 ssh：在第 1 个窗口按 `Enter`，再输入 `~.`（波浪号+点），连接立刻断开；
- Xshell / FinalShell / MobaXterm：**直接关掉第 1 个窗口的标签页**（最简单）。

到**第 2 个窗口**（还连着）检查：

```bash
curl http://localhost:8080
# curl: (7) Failed to connect ...          ← 服务挂了 ❌

pgrep -af http.server   #process grep，专门**按进程名搜索进程**，是简化版的 `ps + grep`
# 没有任何输出 = 进程已经死了
```

**亲眼看到了：SSH 会话一结束，里面的程序跟着死。**

> ⚠️ 查进程用 `pgrep -af 关键词`，**别用** `ps -ef | grep http.server`——后者输出里那行 `grep --color=auto http.server` 是 grep 命令**自己**（它的命令行里也有这几个字），不是你的服务，容易误判。

**为什么会死？** SSH 断开时，系统给会话里所有程序发一个 **SIGHUP（挂断信号）**，意思是"关门了，你们都退出吧"，普通程序收到就退出。下面用你实际敲的 `python3 main.py` 把进程关系讲透。

**用 `python3 main.py` 举个具体例子（搞懂进程父子关系）**

你在 SSH 窗口敲 `python3 main.py` 时，进程关系是这样的：

```
sshd（系统服务，一直跑着，PID 固定）
  └── sshd: lwc@pts/0  ← 你这次 SSH 连接的会话
       └── bash        ← 你的命令行壳（session leader，会话的"老板"）
            └── python3 main.py  ← ★ 你的程序，是 bash 的子进程
```

**每一层的关系**：

| 进程 | 谁启动的 | 归谁管 |
|------|---------|--------|
| `sshd` | 系统开机就启动（systemd 管） | 系统 |
| `sshd: 你的会话` | sshd 给你开的子进程 | sshd |
| `bash` | sshd 登录后帮你启动的壳 | 你的 SSH 会话 |
| `python3 main.py` | **你在 bash 里敲命令启动的** | bash（你的 SSH 会话） |

**关 SSH 窗口时发生了什么**：

```
第 1 步：你关掉 SSH 窗口（或本地断网、合盖子）
        ↓
第 2 步：sshd 发现客户端不见了，结束你的 SSH 会话
        ↓
第 3 步：系统给会话里所有进程发 SIGHUP 信号
        ↓
第 4 步：bash 收到 SIGHUP → 退出
        ↓
第 5 步：python3 main.py 收到 SIGHUP → 退出 ★ 你的程序死了
```

**关键点**：`python3 main.py` 的"老板"是 bash，bash 的"老板"是 SSH 会话。**SSH 会话一没，整条链上的进程都收到 SIGHUP 信号，全部退出**。这不是 Nginx 的问题，也不是 Python 的问题，是 Linux 进程管理的基本规则：**子进程归父进程管，父进程没了子进程也跟着没**。

> 🔑 **一句话记忆**：你在 SSH 里敲的所有命令，都是 SSH 会话的"员工"。**老板（SSH 会话）走了，员工（你的 python 进程）也被遣散**。nohup/systemd 的作用就是让你的程序"脱离"这个会话，自己独立活着。

###### 第 3 步：用 nohup 后台启动（解决问题）

`nohup` = **no hang up**（别挂断），让程序**忽略 SIGHUP 信号**；再加 `&` 放后台、用 `>` 把输出存进日志文件。重新在 SSH 窗口执行：

```bash
cd ~
nohup python3 -m http.server 8080 > app.log 2>&1 &  #这个命名是在关掉窗口1之后执行
# [1] 21971        ← [1] 是后台任务编号，21971 是 PID（每次都不一样）
```

命令逐块拆解：

```
nohup  python3 -m http.server 8080  > app.log  2>&1  &
  ↑                ↑                    ↑          ↑    ↑
忽略挂断信号      要跑的程序          正常输出存日志  报错也进日志 放后台
```

| 部分 | 作用 |
|------|------|
| `nohup` | 让程序忽略 SIGHUP，**SSH 断开也不死**（核心） |
| `python3 -m http.server 8080` | 要跑的程序（以后换成你真实的命令） |
| `> app.log` | 程序正常打印的内容写进 `app.log`（不写会生成 `nohup.out`） |
| `2>&1` | 报错信息也写进同一个日志（否则出错了日志里看不到） |
| `&` | 放到**后台**，终端立刻还给你，能继续敲命令 |

> 💡 `2>&1` 记住固定顺序 `> 文件 2>&1`，不能反过来写。

**启动后立刻验证（关键，别看到任务号就以为成功了）：**

```bash
pgrep -af http.server          # 有 python3 那行输出 = 真的活着
cat app.log                    # 日志正常（Serving HTTP ...），没有报错
curl http://localhost:8080     # 返回 HTML = 服务能访问
```

> ⚠️ `[1] 21971` **只代表"命令已提交后台"，不代表启动成功**。程序若启动失败会立刻退出，屏幕不报错，错误只进日志——所以一定要 `cat app.log` 确认。

###### 第 4 步：证明"用了 nohup，断开也不死"

这次**直接关掉当前 SSH 窗口**（或 `exit` 退出），然后重新连：

```bash
ssh lwc@你的服务器IP
pgrep -af http.server          # 进程还在！✅
curl http://localhost:8080     # 服务还能访问！✅
```

这就是 nohup 的效果：**程序脱离了 SSH 会话，在服务器后台常驻。**

###### 第 5 步：看日志、停服务（善后）

实验服务还开着时，随时可以看日志：

```bash
tail -f app.log                # 实时滚动看日志；按 Ctrl+C 退出查看（不会停服务）
tail -n 50 app.log             # 只看最后 50 行，看完自动退出，不占终端
```

实验完**务必停掉**这个临时服务（它会把家目录文件都共享出去，仅限本机测试，**生产禁用**）：

```bash
sudo ss -lntp | grep 8080      # 按端口查到真实 PID，例如 pid=21971
kill 21971                     # 用你查到的 PID 停掉它
curl http://localhost:8080     # 再访问：Failed to connect = 已停干净
```

> 不想记 PID 也可以按名字停：`pkill -f http.server`（pkill 用法见本章 4.1.1）。

###### 把实验命令换成你真实的程序

日常开发把中间那段换成自己的程序即可，其余 `nohup`、`> 日志 2>&1 &`、验证步骤完全一样：

| 场景 | 启动命令 |
|------|----------|
| Django | `nohup python3 manage.py runserver 0.0.0.0:8000 > dev.log 2>&1 &` |
| Flask | `nohup python3 app.py > app.log 2>&1 &` |
| Java jar | `nohup java -jar myapp.jar > app.log 2>&1 &` |
| Node | `nohup node server.js > app.log 2>&1 &` |
| 过夜长任务（数据迁移/训练） | `nohup python3 migrate.py > migrate.log 2>&1 &` |

> 注意：跑 `python3 app.py` 这种**文件型程序前，先 `ls app.py` 确认文件在当前目录**，否则日志会报 `can't open file 'app.py': No such file or directory`，进程秒退。

###### 常见报错速查

| 报错 / 现象 | 原因 | 解决 |
|-------------|------|------|
| `python3: 未找到命令` | 没装 python3 | 回第 0 步 `sudo yum install -y python3` |
| `Could not resolve host: mirrorlist.centos.org` | yum 源失效 | 先按 7.1.0 节换阿里云源 |
| `-bash: /var/log/app.log: 权限不够` | `/var/log` 只有 root 能写，**重定向失败=程序根本没启动** | 日志写当前目录 `> app.log`（或 `~/`、`/tmp/`） |
| `can't open file 'app.py'` | 当前目录没有这个文件 / 没 cd 对目录 | `ls` 确认文件，或用绝对路径 |
| 显示了 `[1] PID` 但 `pgrep` 查不到 | 程序启动即失败 | `cat 日志` 看真正的报错 |
| 重跑后日志里旧内容没了 | `>` 每次**覆盖**文件 | 想追加用 `>>` |

> 生产环境确实要把日志放 `/var/log/`，让管理员先建子目录授权，**别图省事直接 `sudo nohup ...`**（进程会变成 root 身份，不安全）：
>
> ```bash
> sudo mkdir -p /var/log/myapp && sudo chown lwc:lwc /var/log/myapp
> nohup python3 app.py > /var/log/myapp/app.log 2>&1 &
> ```

**别用 nohup 跑的东西**：MySQL、Nginx、Tomcat 这类正式服务，或要 7×24 稳定运行的线上后端——它们用下面的 systemd 托管（崩溃自动重启、开机自启）。

##### 方法二：systemd 写服务 —— 生产环境（一步一步做）

nohup 解决了"SSH 断开程序不死"，但还有三个问题没解决：**崩溃了不自动重启、服务器重启不自动起来、日志不会自动轮转**。生产环境的正式服务要用 systemd 托管，下面一步一步做。

**常见疑问：我把项目放到 Nginx 里了，打开网站一直能访问，还需要这个吗？**

> 🏷️ ⭐ 开发必会 —— 搞清楚"静态文件"和"后端进程"的区别，否则永远不理解为什么要 systemd

**先说结论**：**纯静态网站不需要，但有后端的网站必须要。**

**关键概念：Nginx 只管文件，不管你的后端代码**

| 东西 | 是什么 | 需不需要"跑着" |
|------|--------|---------------|
| **Nginx** | 系统服务（yum 装时已自动注册 systemd） | ✅ 一直跑着（你不用管） |
| **Vue dist 静态文件** | 一堆 HTML/CSS/JS 文件 | ❌ 文件是"死的"，Nginx 直接读 |
| **Django/Flask/Node 后端** | 你的业务代码（Python/Node 进程） | ✅ 必须有进程在跑才能执行 |

**两种部署场景对比**：

**场景 1：纯静态网站（只有前端，没有后端）**
```
浏览器 → Nginx → 直接读 /www/dist/index.html 返回
```
→ **不需要 systemd 管你的代码**，因为根本没有"你的代码进程"，只有 Nginx 在跑（它已经是系统服务了）。

**场景 2：前后端分离网站（Vue + Django/Flask）**
```
浏览器请求 /           → Nginx 读 dist/index.html（静态，没问题）
浏览器请求 /api/users/ → Nginx 转发给 127.0.0.1:8000 → Django 进程执行代码返回 JSON
                                                              ↑
                                                    ★ 这个进程没了就 502
```
→ **必须用 systemd 管 Django 进程**，因为它是一个独立的 Python 进程，不是 Nginx 的一部分。

**具体发生了什么**：机制和前面讲的完全一样（SSH 断开 → SIGHUP → Django 进程退出）。唯一容易误导的是——**Nginx 还活着**，所以静态页面能打开，让你以为"网站还在运行"，但点任何需要后端的功能就 **502 Bad Gateway**。这就是为什么后端必须用 systemd 托管。

> 🔑 **一句话记忆**：**Nginx 管静态文件，systemd 管你的后端进程**。Nginx 已经是系统服务不用你管，但你的 Django/Flask/Node 是独立进程，必须用 systemd 托管才能 7×24 跑。

**核心思路**：你不用直接跑程序，而是写一个 `xxx.service` 配置文件告诉 systemd"这个程序怎么启动"，然后让 systemd 去跑它。以后你只管 `systemctl start/stop/restart` 就行。

**和 nohup 的本质区别**：

| | nohup + & | systemd |
|--|-----------|---------|
| 谁在管进程 | 你自己（启动后就不管了） | systemd（PID=1，系统总管，全天候盯着） |
| 崩溃了 | 死了就死了 | **自动重启** |
| 服务器重启 | 服务不会自己起来 | **开机自启** |
| 日志 | 你自己 `> xxx.log` 重定向 | **journalctl 统一管**，自动轮转 |
| 适合 | 临时任务、调试、过夜脚本 | **生产环境正式服务** |

###### 第 1 步：准备一个要托管的程序

用前面实验的 `python3 -m http.server 8080` 当例子（真实项目换成你的 Django/Flask/Node 启动命令）。先确认命令能直接跑：

```bash
python3 -m http.server 8080
# Serving HTTP on 0.0.0.0 port 8080 ...
```

按 `Ctrl+C` 停掉，准备交给 systemd。

###### 第 2 步：写 .service 配置文件

systemd 的服务配置文件统一放在 `/etc/systemd/system/` 下，文件名就是服务名（比如 `myapp.service`，以后命令里就用 `myapp`）。

```bash
sudo vi /etc/systemd/system/myapp.service
```

粘贴以下内容（**逐行注释，每一行都有什么用**）：

```ini
# ===== 第 1 段：[Unit] 描述这个服务是什么、依赖什么 =====
[Unit]
Description=My Python Web App            # 服务描述，systemctl status 时显示
After=network.target                     # 等网络就绪后再启动（Web 服务都要等网络）

# ===== 第 2 段：[Service] 核心：程序怎么跑 =====
[Service]
Type=simple                              # 程序类型：simple=前台跑就行（最常用）
User=nginx                               # 用哪个用户跑（别用 root！用专门的用户如 nginx/www）
WorkingDirectory=/www/myproject          # 程序的工作目录（相当于 cd 到这里再跑）
ExecStart=/usr/bin/python3 -m http.server 8080   # ★ 启动命令（必须写绝对路径！）
Restart=always                           # 崩溃/退出后自动重启（生产必加）
RestartSec=3                             # 重启前等 3 秒（防止崩了疯狂重启）
Environment=APP_ENV=production           # 环境变量（可写多行，如 DB 密码）
Environment=DB_HOST=127.0.0.1

# ===== 第 3 段：[Install] 开机自启相关 =====
[Install]
WantedBy=multi-user.target               # 多用户模式下自启（几乎所有服务都写这个）
```

> ⚠️ **3 个最容易踩的坑**：
> 1. **`ExecStart` 必须写绝对路径**：`/usr/bin/python3` 而不是 `python3`。用 `which python3` 查绝对路径。
> 2. **`User` 别写 root**：用专门的低权限用户（如 nginx、www-data），被入侵了危害小。
> 3. **`WorkingDirectory` 要写对**：程序里用相对路径读配置文件时，会从这个目录找。

##### 哪些字段每个项目都要改，哪些可以照抄？

> 🏷️ ⭐ 开发必会 —— 以后写新服务时，照着这个表改就行，不用每次都重新理解

**按"变不变"分三类**：

| 字段 | 变不变 | 怎么改 | 例子 |
|------|--------|--------|------|
| `Description` | ✅ 改 | 改成你的服务名，方便 `systemctl status` 识别 | `Description=Django Blog API` |
| `User` | ✅ 可能改 | 看你的程序用哪个用户跑（有上传文件/写日志的需求时要对应用户） | `User=nginx` / `User=lwc` |
| `WorkingDirectory` | ✅ **必改** | 改成你项目的实际路径，程序里的相对路径都基于它 | `WorkingDirectory=/www/myproject/backend` |
| `ExecStart` | ✅ **必改** | 改成你项目真实的启动命令 | `ExecStart=/usr/bin/python3 manage.py runserver 0.0.0.0:8000` |
| `Environment=...` | ✅ **必改** | **每个项目需要的环境变量完全不同**，没有就删掉，有多就加多行 | 见下方详解 |
| `After=network.target` | ❌ 不用改 | Web 服务都要等网络，照抄 | — |
| `Type=simple` | ❌ 不用改 | 99% 的 Web 服务都是 simple，照抄 | — |
| `Restart=always` | ❌ 不用改 | 生产必加自动重启，照抄 | — |
| `RestartSec=3` | ❌ 不用改 | 重启间隔 3 秒足够，照抄 | — |
| `WantedBy=multi-user.target` | ❌ 不用改 | 几乎所有服务都写这个，照抄 | — |

**`Environment` 详解（最容易困惑的字段）**：

`Environment=KEY=VALUE` 是给你的程序传**环境变量**。你的程序代码里 `os.environ.get('DB_HOST')` 或 `process.env.DB_HOST` 读到的值，就是从这里来的。

- **不是每个项目都需要**：如果你的程序硬编码了配置（不读环境变量），这两行可以**整个删掉**
- **需要什么写什么**：你的项目代码里读了哪些环境变量，就写哪些。没读的写了也没用
- **可以写多行**：每个变量一行，写多少都行

**不同项目的 Environment 对比**：

| 项目类型 | 可能需要的 Environment | 说明 |
|---------|----------------------|------|
| Django | `Environment=DJANGO_SETTINGS_MODULE=myproject.settings.prod`<br>`Environment=DB_NAME=mydb`<br>`Environment=DB_USER=myuser`<br>`Environment=DB_PASSWORD=你的密码` | Django settings 里从环境变量读数据库配置 |
| Flask | `Environment=FLASK_ENV=production`<br>`Environment=DATABASE_URL=mysql://user:pass@127.0.0.1/db` | Flask 常用 `DATABASE_URL` 一个变量搞定 |
| Node.js | `Environment=NODE_ENV=production`<br>`Environment=PORT=3000`<br>`Environment=DB_HOST=127.0.0.1` | Node 项目常用 `process.env.xxx` 读 |
| Java Spring Boot | `Environment=SPRING_PROFILES_ACTIVE=prod`<br>`Environment=SPRING_DATASOURCE_URL=jdbc:mysql://...` | Spring Boot 配置前缀都是 SPRING_ |
| 纯 Python 脚本（如 http.server） | **不需要 Environment** | 没有配置要传，直接删掉这两行 |

> ⚠️ **安全提醒**：密码/密钥写在 Environment 里是明文存在 `.service` 文件里的。`/etc/systemd/system/` 默认只有 root 能读（644），还算安全，但别把 `.service` 文件提交到 Git。更安全的做法是用 `EnvironmentFile=/etc/myapp/secrets` 把密钥放单独文件，权限设 600。

**快速判断口诀**：**`Description`、`User`、`WorkingDirectory`、`ExecStart`、`Environment` 这 5 个是"要动脑改"的；其余 5 个（After、Type、Restart、RestartSec、WantedBy）是"无脑照抄"的。**

###### 第 3 步：让 systemd 加载新配置

```bash
sudo systemctl daemon-reload
# 无输出 = 成功。以后每次改了 .service 文件都要执行这一步
```

> 🔑 **记忆**：改了 `.service` 文件 → 必须 `daemon-reload` 让 systemd 重新读；改了**程序代码**（比如重新打包上传了）→ 只需 `systemctl restart myapp`，不用 reload。

###### 第 4 步：启动 + 开机自启

```bash
sudo systemctl start myapp          # 现在立刻启动
sudo systemctl enable myapp         # 设为开机自启
# 或者一步到位：
sudo systemctl enable --now myapp   # 开机自启 + 现在就启动
```

###### 第 5 步：验证服务跑起来了

```bash
# ① 看状态（最常用）
sudo systemctl status myapp
# 看到 "active (running)" + 绿色 = 正常
# 看到 "failed" 红色 = 启动失败，看下面的错误信息

# ② 看服务日志（程序的 stdout/stderr 都在这里）
sudo journalctl -u myapp -f          # -f 实时滚动（= tail -f）
sudo journalctl -u myapp -n 50       # 看最近 50 行
sudo journalctl -u myapp --since today   # 看今天的

# ③ 实际访问测试
curl http://localhost:8080
# 返回 HTML = 服务正常
```

###### 第 6 步：日常操作速查

```bash
sudo systemctl restart myapp         # 改完代码后重启
sudo systemctl stop myapp            # 停止
sudo systemctl disable myapp         # 取消开机自启（但还会运行）
sudo systemctl disable --now myapp   # 取消自启 + 现在就停

# 彻底删除服务：
sudo systemctl stop myapp
sudo systemctl disable myapp
sudo rm /etc/systemd/system/myapp.service
sudo systemctl daemon-reload
```

**记住一句话**：**临时跑脚本/过夜任务 → nohup；线上正式服务 → systemd**。生产环境别用 nohup 跑后端服务，半夜崩了你都不知道。

### 1.3 进程状态（Linux 实际状态）（必会）
> 🏷️ ⭐ 开发必会 —— 看懂 `ps` 和 `top` 里的 STAT 列即可

Linux 进程有 4 种主要状态，对应 `ps` 的 STAT 字段：

| 状态码 | 名称 | 说明 | 你看到说明什么 |
|--------|------|------|------|
| **R** | Running | 运行中或就绪 | 进程正在用 CPU 或排队等 CPU |
| **S** | Sleep | 可中断休眠 | **最常见**，进程在等事件（网络、磁盘、定时器），大部分服务都是这个状态 |
| **T** | Stopped | 停止 | 按 Ctrl+Z 暂停的进程，或被调试器 attach |
| **Z** | Zombie | 僵尸 | 已退出但父进程还没回收，长期大量 Z 是程序 bug |

> 💡 开发岗知道 R/S/T/Z 四个就够。`D`（不可中断休眠，磁盘卡死时出现）和 `I`/`P`（内核线程状态）运维才关心，开发遇不到。

##### 实战：一条命令看系统进程状态分布

```bash
ps -eo stat,pid,cmd | head -20
```

**逐块拆解：**

```
ps  -eo  stat,pid,cmd  |  head -20
 ↑    ↑       ↑         ↑     ↑
命令  选项   要显示的列  管道  只看前 20 行
```

| 部分 | 含义 | 说明 |
|------|------|------|
| `ps` | 命令本身，Process Status | 查看进程信息的工具 |
| `-e` | **every**，显示**所有**进程（不只你自己的） | 不加 `-e` 只能看到当前终端启动的进程，很少 |
| `-o` | **output**，指定**输出哪些列、按什么顺序** | ps 默认输出很多列，用 `-o` 可以自己挑只看需要的 |
| `stat,pid,cmd` | 要显示的三列，逗号隔开 | stat=状态、pid=进程号、cmd=启动命令（比默认的 args 更短更直观） |
| `\|` | 管道，把左边的输出喂给右边 | 见第二章 2.15.4 节 |
| `head -20` | 只取前 20 行 | 不加的话机器上 200+ 个进程全列出来，刷屏看不完 |

**跑起来输出长这样（你可以现在就在终端敲一下试试）：**

```
STAT   PID CMD
S        1 /usr/lib/systemd/systemd --switched-root --system --deserialize 22
S        2 [kthreadd]
S        3 [ksoftirqd/0]
S        5 [kworker/0:0H]
S        7 [migration/0]
S       11 [rcu_sched]
S       12 [rcu_bh]
R     12345 ps -eo stat,pid,cmd              ← 只有这个 R，就是 ps 自己在跑
S     1024 mysqld --daemonize --skip-networking=0 --socket=/var/lib/mysql/mysql.sock
S     2048 nginx: master process /usr/sbin/nginx
```

**怎么读这几行：**

| 看到什么 | 说明什么 |
|----------|----------|
| `S` 占绝大多数 | **正常**！99% 的进程在休眠等事件，不占 CPU |
| `R` 只有 1 个（就是 `ps` 自己） | **CPU 很闲**，没有业务在计算 |
| `Z` 持续出现 | **有 bug**！某个父进程没回收子进程，要修代码 |
| `D` 出现几个 | 磁盘 I/O 卡了，数据库或日志在大量写 |

> 💡 想数一下各状态有多少个？用管道再串一层：`ps -eo stat | sort | uniq -c`，会输出类似 `234 S  1 R  0 Z` 的统计，一眼看清分布。

##### 常见疑问：为什么我看自己的进程全是 S，一个 R 都没有？（必会）

> 🏷️ ⭐ 开发必会 —— 这是正常现象，不是你的机器有问题，也不是命令错了

**先说结论**：**R 状态转瞬即逝，`ps` 是"拍快照"，极难抓到 R**。你看到全是 S 完全正常。

**为什么 R 这么难抓**：

| 状态 | 持续时间 | 为什么 |
|------|---------|--------|
| **S（休眠）** | 毫秒 ~ 小时 | 进程在等事件（等网络包、等磁盘、等定时器），大部分时间都在这 |
| **R（运行）** | **微秒级** | 进程真正用 CPU 的时间极短，现代 CPU 每秒执行几十亿条指令 |

举个具体例子：一个 Python Web 服务处理一次请求可能这样：

```
等请求（S，持续 100ms）→ 处理请求（R，持续 0.5ms）→ 写日志（S，持续 2ms）→ 等下一个请求（S，持续 100ms）...
```

R 只占整个生命周期的 **0.5% 不到**。`ps` 拍一次快照要花几毫秒，这几毫秒里进程大概率处于 S，所以你抓不到 R。

**连 `ps` 自己都可能不是 R**：`ps` 命令执行时先收集所有进程信息（这期间可能被调度出去变成 S），收集完才打印。你看到的快照是"收集完成那一刻"的状态，此时 `ps` 可能已经准备退出了，所以连 `ps` 自己都显示成 S 或干脆没出现在列表里（已经退出）。

**怎么才能稳定看到 R 状态**：

```bash
# 方法 1：用 top（持续刷新，每 1~3 秒拍一次，概率高很多）
top
# 按 P 键按 CPU 排序，最上面那行一般是 R

# 方法 2：开一个死循环占住 CPU（造一个稳定的 R 进程）
# 开 SSH 窗口 1：
while true; do :; done      # 死循环，持续占一个 CPU 核
# 开 SSH 窗口 2：
ps -eo stat,pid,cmd | grep while
# R  12345 bash -c while true; do :; done    ← 这次能稳定看到 R

# 方法 3：ps 循环拍，多拍几次总能抓到
for i in $(seq 1 50); do ps -eo stat | grep -c R; done
# 输出 50 个数字，大部分是 0，偶尔出现 1 或 2
```

> ⚠️ **方法 2 的死循环会占满一个 CPU 核**，看完记得在窗口 1 按 `Ctrl+C` 停掉，否则机器会变卡。

**记住一句话**：**`ps` 看到全是 S = 系统很闲，正常；看到一堆 R = CPU 很忙，要排查**。不要因为"看不到 R"就怀疑自己命令敲错了。

### 2.1 ps 命令的两种风格（必会）
> 🏷️ ⭐ 开发必会 —— 软件开发日常高频使用，务必掌握

ps 有三种语法流派，初学者常因混淆而困惑：

| 流派 | 语法 | 来源 | 典型命令 |
|------|------|------|----------|
| **BSD 风格** | 选项**不加横线** | BSD Unix | `ps aux`、`ps ax` |
| **System V 风格** | 选项**加横线** | UNIX 标准 | `ps -ef`、`ps -el` |
| **GNU 风格** | 选项加双横线 | GNU 扩展 | `ps aux --sort=-%cpu` |

```bash
# BSD 风格（最常用）
ps aux         # 查看所有进程（a=所有终端，x=无终端进程，u=用户格式）
ps ax          # 不显示用户列

# System V 风格
ps -ef         # 显示所有进程（e=所有，f=完整格式含父子关系）
ps -eH         # 显示进程层级
ps -el         # 长格式

# ⚠️ 不要混用横线：ps -aux 是错误的（-a 在 System V 中表示"所有终端"，
# 但 BSD 的 aux 中 aux 是一个组合，加横线含义会变化）
```

#### 2.1.1 两种风格的输出对比

```bash
# BSD 风格：ps aux → 字段 USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND
# System V 风格：ps -ef → 字段 UID PID PPID C STIME TTY TIME CMD
# 关键区别：ps -ef 直接显示 PPID（父进程），ps aux 不显示但更详细
```

### 2.2 ps aux 输出解读（必会）
> 🏷️ ⭐ 开发必会 —— 软件开发日常高频使用，务必掌握

```
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root         1  0.0  0.1  128496  6896 ?        Ss   08:00   0:01 /sbin/init
root         2  0.0  0.0      0     0 ?        S    08:00   0:00 [kthreadd]
mysql     1234  5.2  10.5 892345 51234 ?       Sl   08:01   5:23 /usr/sbin/mysqld
```

**字段说明：**
| 字段 | 说明 |
|------|------|
| USER | 进程所有者 |
| PID | 进程ID |
| %CPU | CPU占用率 |
| %MEM | 内存占用率 |
| VSZ | 虚拟内存大小 |
| RSS | 实际物理内存 |
| TTY | 终端号（**很多是 `?`，见下方详解**） |
| STAT | 进程状态 |
| START | 启动时间 |
| TIME | CPU使用时间 |
| COMMAND | 启动命令 |

**TTY 为什么很多是 `?`？（必会）**

> 🏷️ ⭐ 开发必会 —— 这是正常现象，不是进程出问题了

TTY = Teletype（电传打字机，Linux 继承的老名字），表示**这个进程是从哪个终端启动的、归哪个终端管**。

| TTY 显示 | 含义 | 例子 |
|----------|------|------|
| `?` | **没有控制终端**（最常见） | systemd、nginx、mysql、sshd、内核线程 |
| `pts/0`、`pts/1` | 伪终端（SSH 远程登录的窗口） | 你在 SSH 里敲的命令 |
| `tty1`、`tty2` | 物理控制台终端（服务器接的显示器+键盘） | 本机直接登录敲的命令 |

**为什么 `?` 占绝大多数**：服务器上跑的大部分进程根本不需要终端——

1. **守护进程**（systemd、nginx、mysqld、sshd）：开机就由 systemd 拉起，从来没连过终端，所以是 `?`
2. **后台进程**（nohup 启动的、systemd 托管的你的 Django/Node）：启动后脱离了终端，也是 `?`
3. **内核线程**（kthreadd、ksoftirqd 等）：内核自己的线程，更没有终端

**只有你在 SSH 窗口里直接敲命令启动的前台进程，TTY 才会显示 `pts/N`**。比如用前面实验过的 `python3 -m http.server 8080`：

```bash
# 你在 SSH 窗口直接敲（前台或 & 后台都行，只要没脱离终端）：
python3 -m http.server 8080 &

# ps aux 看到：
lwc    12345  ...  pts/0   S   ...  python3 -m http.server 8080
#                              ↑ 显示 pts/0，因为是从你的 SSH 窗口启动的

# 但如果用 nohup 或 systemd：
lwc    12346  ...  ?       S   ...  python3 -m http.server 8080
#                        ↑ 显示 ?，因为脱离了终端
```

> 🔑 **一句话记忆**：**`?` = 没有终端的后台/服务进程，正常；`pts/N` = 你当前 SSH 窗口启动的进程**。看到一堆 `?` 说明系统服务都在正常后台跑着。

**进程状态码（STAT 列重点认这 5 个，R/S/T/Z 详见 1.3）：**
| 状态 | 说明 |
|------|------|
| R | 运行中 |
| S | 休眠中（可被唤醒），最常见 |
| D | 不可中断休眠（通常在等磁盘 I/O） |
| Z | 僵尸进程 |
| T | 停止 |

**STAT 列后缀字母详解（必会）**

> 🏷️ ⭐ 开发必会 —— STAT 列 = 第 1 个字符（主状态）+ 后面的字符（附加标志）。截图里的 `Ss`、`S<` 都是"S 休眠 + 后缀"

**你截图里 3 种状态的逐字拆解**：

| 显示 | 第 1 字符 | 后缀 | 完整含义 |
|------|----------|------|---------|
| `S` | S = 休眠 | （无） | 普通休眠进程，最常见 |
| `Ss` | S = 休眠 | `s` = 会话首领 | 休眠 + 它是某个会话的领头进程（比如 bash 壳） |
| `S<` | S = 休眠 | `<` = 高优先级 | 休眠 + 优先级高于普通进程（内核线程、root 进程常见） |

**完整后缀字母表**（不用背，需要时查表）：

| 后缀 | 含义 | 常见在哪 |
|------|------|---------|
| `s` | session leader，会话首领 | bash、sshd 子进程等"带头"的进程 |
| `<` | 高优先级（nice 值 < 0） | 内核线程、root 启动的关键服务 |
| `N` | 低优先级（nice 值 > 0） | 用 `nice -n 10` 启动的后台低优先级任务 |
| `l` | 多线程进程 | Java、Node、Go 服务（基本都带 l） |
| `+` | 前台进程组 | 你当前 SSH 窗口正在跑的命令 |
| `L` | 有内存页被锁定（不能换出到 swap） | 数据库等需要实时响应的程序 |
| `I` | 空闲内核线程（Linux 4.14+） | 内核空闲线程，系统闲时出现 |

**实战怎么看**：

```bash
ps aux | head
# 看到 Ss  → 某个会话的领头进程在休眠（比如你的 bash）
# 看到 S<  → 高优先级进程在休眠（内核线程居多，正常）
# 看到 Sl  → 多线程服务在休眠（Java/Node 后端，正常）
# 看到 S+  → 你当前终端前台跑的命令在休眠（比如一个卡住的 cat）
```

> 🔑 **一句话记忆**：**第 1 个字母看状态（R/S/D/Z/T），后面的字母看属性**。最常见的组合是 `S`（普通休眠）、`Ss`（会话首领休眠）、`Sl`（多线程休眠）、`S<`（高优先级休眠），全是正常现象。

### 2.3 常用 ps 组合（必会）
> 🏷️ ⭐ 开发必会 —— 开发高频就这 4 个

```bash
# 查看特定进程（最高频，grep -v grep 是排除 grep 自己那行）
ps aux | grep nginx
ps aux | grep -v grep | grep java

# 看父子关系（带 PPID 列）
ps -ef | grep java

# 按 CPU / 内存占用排序，找最耗资源的进程
ps aux --sort='-%cpu' | head -20
ps aux --sort='-%mem' | head -20
```

> ⚠️ **`%cpu` 必须加引号**：不加引号时 `%` 在 zsh 等 shell 里会被当成作业控制字符，导致报错或无输出。bash 里有时也会出问题，**养成加单引号的习惯**。如果还不行，用 `pcpu`/`pmem` 替代（等价）：
> ```bash
> ps aux --sort=-pcpu | head -20
> ps aux --sort=-pmem | head -20
> ```
> **另外别忘了加 `aux`**：只敲 `ps --sort=-%cpu` 只会显示当前终端的进程，基本看不到东西。

**最后两条排序命令逐块拆解：**

```
ps  aux          --sort='-%cpu'      | head -20
↑   ↑↑↑          ↑                    ↑
查看  三个固定选项  按%CPU列，-表示从大到小   只取前20行，防止刷屏
```

| 片段 | 含义 |
|------|------|
| `ps` | 查看进程 |
| `a` | 列出**所有终端**上的进程（不只当前终端） |
| `u` | 用户友好格式，带出 `%CPU`、`%MEM`、`USER` 等列 |
| `x` | 连**无终端的后台服务**也列出来（mysqld、nginx 不加 x 会漏） |
| `--sort=-%cpu` | 按 CPU 列排序，**开头 `-` = 从大到小**；去掉 `-` 则从小到大 |
| `--sort=-%mem` | 同上，换成按**内存**排序 |
| `\| head -20` | 只看前 20 行（进程有几百个） |

> `aux` 是固定组合，整体意思 = **列出系统所有进程 + 带 CPU/内存详情列**，不用纠结单个字母。

输出重点看三列：`%CPU`/`%MEM`（谁最耗资源）、`COMMAND`（哪个程序），拿到最上面那个进程的 `PID` 就能去 `kill PID`。

**使用场景：**

- 机器突然卡 → `--sort=-%cpu` 看谁占满 CPU
- 内存快满 → `--sort=-%mem` 看谁吃内存（Java 堆过大、Python 泄漏常见）

> 💡 等价办法：直接用 `top`，进去按 `P` 按 CPU 排序、按 `M` 按内存排序、`q` 退出。`ps ... | head` 适合只看一眼/截图，`top` 适合持续观察。

## 3. 父子进程（了解即可）
> 🏷️ 开发极少需要深度理解，知道 PPID 是啥、怎么查就够

Linux 里进程是"一生二"拉起来的：`systemd`（PID 1，系统第一个进程）启动各个服务，你在终端敲的命令由 `bash` 拉起。每个进程除了 PID，还有一个 **PPID（Parent PID，父进程 ID）**——谁把它拉起来的。

```bash
# 查某个进程的 PID 和它的父进程 PPID（极少用，知道这条命令存在就行）
ps -o pid,ppid,cmd -p 1234
# 输出示例：PID 1234, PPID 1024, 命令 java -jar myapp.jar
# → 这个 java 进程是 PID 1024 的进程拉起来的
```

> 💡 什么时候会用到？排查僵尸进程（见 1.3 节）时需要找到父进程重启它；或搞不清"这个进程是谁拉起来的、为什么还在跑"时看一下。日常开发**几乎不用**。

## 4. 终止进程（必会）
> 🏷️ ⭐ 开发必会 —— 软件开发日常高频使用，务必掌握

### 4.1 kill 命令 + 信号（必会）

`kill` 不是"杀进程"，它是给进程发**信号**（Signal）——进程收到信号后自己决定怎么处理。记住两个规则：

- **kill 默认发 SIGTERM(15)**：请求进程"你该关门了，先做清理再退出"。进程可以捕获这个信号，先保存数据、关闭文件、断开连接，然后优雅退出。
- **kill -9 发 SIGKILL(9)**："你别废话了，内核直接回收你"。进程**没法捕获、没法拒绝**，数据可能丢失，只能当最后手段。

开发只需记住 3 个信号：

| 信号 | 编号 | 用途 |
|------|------|------|
| **SIGTERM** | 15 | **kill 默认发的**，让进程优雅退出 |
| **SIGKILL** | 9 | **kill -9** 强制杀，进程没法拒绝 |
| **SIGHUP** | 1 | 不杀进程，让它**重读配置**（如 nginx 平滑 reload） |

**实际用：**

```bash
# ① 正常终止（让进程自己清理）—— 90% 场景用这条就够
kill 1234

# ② 强制终止（最后手段，kill 3 秒后还没死才用）
kill -9 1234

# ③ 不知道 PID，按名字杀——pkill 详解见下面单独小节
pkill nginx
pkill -f "java -jar myapp"

# ④ 改完 nginx 配置想生效，不中断服务（生产常用）
nginx -s reload                # nginx 自带写法，等价于 kill -HUP $(cat /var/run/nginx.pid)
```

#### `kill 1234` 里的 1234 是什么？—— 是从 ps 查出来的 PID

`1234` 只是举例用的**占位数字**，代表要杀进程的 **PID（Process ID，进程编号）**——系统给每个运行中的程序分配的唯一"身份证号"，PID 1 永远是 systemd，其他程序从 2 往后排，**每次启动都会变**。

**这个数字不是凭空写的，要先用 ps 查出来，再抄给 kill：**

```bash
# 第 1 步：查进程，找到目标的 PID（ps aux 输出的【第 2 列】就是 PID）
ps aux | grep nginx
# USER   PID    %CPU %MEM  COMMAND
# root   1234   0.0  0.1   nginx: master process
#        ↑↑↑↑
#       就是它

# 第 2 步：把查出来的数字填到 kill 后面
kill 1234

# 第 3 步：再查一次，那行没了 = 杀掉了
ps aux | grep nginx
```

也可以用前面学的 `pgrep` 直接拿 PID，省得肉眼找列：

```bash
pgrep -f nginx            # 直接打印出 PID 号，例如 1234
kill $(pgrep -f nginx)    # 进阶写法：把查到的 PID 直接喂给 kill
```

**为什么 kill 认 PID 不认名字？** 因为可能有**一堆同名进程**（nginx 常是 1 个 master + 几个 worker），用 PID 能**精准杀某一个**；想按名字一锅端才用 `pkill nginx`：

| 需求 | 命令 | 效果 |
|------|------|------|
| 精准杀某一个 | `kill 1234`（先 ps/pgrep 查 PID） | 只杀 PID=1234 |
| 按名字全杀掉 | `pkill nginx` | 所有叫 nginx 的都杀 |
| 普通 kill 杀不掉 | `kill -9 1234` | 强杀兜底 |

> 📌 全课件出现的 `kill 1234`、`kill 12345`、`kill 21971` 都是占位示例，**实际操作时一律换成你自己 ps/pgrep 查出来的真实 PID**，不要照抄数字（那个进程很可能根本不存在，会报 `No such process`）。

### 4.1.1 pkill 深度讲解（`-f` 到底啥意思）

pkill 和 kill 唯一区别：kill 要 PID 号，pkill 给名字就行。但 pkill 有两种匹配模式，新手最懵的就是 `-f`。

#### 先建一个测试场景

假设你服务器上**同时跑着 3 个 Java 程序**（都是 java 进程，但启动命令不同）：

```bash
# 进程 A：用户 alice 跑的旧版后台
alice  1024 java -jar /opt/app/old-backend.jar --port=8080

# 进程 B：你自己跑的新版测试
root   2048 java -jar /opt/app/new-backend.jar --port=8081

# 进程 C：Tomcat（也是 java 进程）
root   3072 java -Dcatalina.home=/usr/local/tomcat -jar /usr/local/tomcat/bin/bootstrap.jar
```

#### 不带 -f：只看进程名

```bash
pkill java
```

**匹配逻辑**：只看进程的**名字**字段（executable name，就是可执行文件名，最多 15 个字符）。三个进程的名字都是 `java`，所以：

> 🔴 **三个全杀！** old-backend、new-backend、Tomcat 一起死

这显然不是你想要的——你可能只想杀 new-backend 那一个。

#### 带 -f：看整条命令行

```bash
pkill -f "java -jar /opt/app/new-backend.jar"
```

`-f` = **full**，匹配完整的命令行（进程启动时的整条命令字符串）。每个进程的完整命令行是不同的：

| 进程 | 完整命令行 | 匹配 `java -jar /opt/app/new-backend.jar`？ |
|------|-----------|---------------------------------------------|
| A | `java -jar /opt/app/old-backend.jar --port=8080` | ❌ |
| B | `java -jar /opt/app/new-backend.jar --port=8081` | ✅ |
| C | `java -Dcatalina.home=/usr/local/tomcat -jar ...` | ❌ |

> 🟢 **只杀 B！** old-backend 和 Tomcat 安然无恙

#### 再对比一张表，彻底搞懂

| 命令 | 匹配范围 | 上面场景杀谁 | 什么时候用 |
|------|----------|-------------|-----------|
| `pkill java` | 进程名叫 java 的**所有**进程 | A、B、C 全杀 | 只有当你确定"机器上**不应该有任何 java 进程**"时才用 |
| `pkill nginx` | 进程名叫 nginx 的所有进程 | （不适用） | nginx 的 worker/master 都叫 nginx，全杀没问题 |
| `pkill -f "new-backend"` | 命令行里含 new-backend 的 | **只杀 B** | 多个 java/python 程序同时跑时，精准杀某一个 |
| `pkill -f "python"` | 命令行里含 python 的 | 所有 python 进程都杀 | 只有一个 python 程序时没问题，多个时要小心 |

#### pkill 的"预览模式"：pgrep

pkill 有个配套命令 **pgrep**，参数一模一样，但**只查不杀**。敲 pkill 之前先 pgrep 确认：

```bash
# 想杀 new-backend，先看"将要杀的是谁"
pgrep -af "new-backend"
# 输出：2048 root java -jar /opt/app/new-backend.jar --port=8081
# ↑ 2048 是 PID，-a 显示完整命令行，-f 按命令行匹配

# 确认就是你要杀的那个，再执行
pkill -f "new-backend"
```

> 💡 **养成习惯**：pkill 前先 pgrep -af 看一眼。生产环境误杀进程可能导致服务中断。

#### pkill 和 killall 的关系

`killall nginx` = `pkill nginx`，效果一样。但 pkill 多了 `-f`（按命令行匹配）、`-u`（只杀某用户的进程）等选项，更灵活。**推荐统一用 pkill**。

> ⚠️ **pkill -f 容易误杀的典型例子**：你敲 `pkill -f "python"`，结果你自己正在跑的 `python3 test.py`（如果也是 nohup 起的）也被杀了。或者你敲 `pkill -f "8080"`，两个进程的命令行都含 8080（`--port=8080`），全杀。**关键词越具体越安全**——用 `pkill -f "myapp.jar"` 而不是 `pkill -f "java"`。

**kill 和 systemctl 怎么分工：**

| 场景 | 用什么 |
|------|--------|
| 正式服务（MySQL/Nginx/Tomcat） | **优先 `systemctl stop xxx`**——会走正规停止流程（发 SIGTERM、等清理、超时再 SIGKILL） |
| 自己跑的临时脚本（nohup 起的） | `kill PID` → 不行再 `kill -9 PID` |
| 卡死了、systemctl stop 等半天没反应 | `kill -9 PID` 兜底 |

### 4.2 优雅终止流程（必会）

别一上来就 `kill -9`，给进程留机会清理：

```bash
# 步骤 1：先查 PID
ps aux | grep myapp

# 步骤 2：发 SIGTERM，让它优雅退出
kill 1234

# 步骤 3：等 3 秒，确认还在不在
sleep 3
ps -p 1234                       # 没输出就是已死

# 步骤 4：还在？强制杀
kill -9 1234
```

> 💡 **kill -9 的风险**：进程没机会保存数据（数据库事务回滚、日志丢失）、没机会关闭文件/网络连接、子进程可能变孤儿。**只作为最后手段**，别养成 `-9` 随手加的坏习惯。

### 4.3 后台进程管理（了解即可）

按 `Ctrl+Z` 暂停前台进程，用 `&` 放后台——这些是 shell 的作业控制，开发偶尔用：

```bash
jobs                   # 查看当前 shell 的后台任务列表
fg %1                  # 把后台任务 1 切回前台（继续交互）
bg %1                  # 把暂停的任务 1 放到后台继续跑
kill %1                # 杀掉后台任务 1（不用找 PID，用 % 编号就行）
```

> 💡 日常开发更常用的是 `nohup`（1.2.1 节）或 `systemctl`，job control 只在"不小心按了 Ctrl+Z 把程序挂起了"时偶尔救一下。

## 5. 服务管理（必会）
> 🏷️ ⭐ 开发必会 —— 让 MySQL/Tomcat/Nginx 启动、停止、开机自启，全靠 systemctl

### 5.1 systemctl 常用命令（必会）
> 🏷️ ⭐ 开发必会 —— 开发记这一组命令就够，systemd 底层原理不用深究

**先理清三个名词：**

| 名词 | 是什么 | 类比 |
|------|--------|------|
| **systemd** | CentOS 7 以后的"服务大管家"（PID=1 的那个系统进程），负责启动/停止/守护所有后台服务 | 公司的**后勤总管** |
| **systemctl** | 你用来**指挥** systemd 的命令（control） | 给总管打电话用的**对讲机** |
| **服务（service / unit）** | 被管理的一个后台程序，如 nginx、mysqld，对应一个 `xxx.service` 配置文件 | 总管手下的每个**员工** |

你不会直接操作 systemd，**所有操作都通过 `systemctl` 命令**完成。

**命令通用格式：**

```
systemctl   动作   服务名
   ↑         ↑       ↑
 对讲机    start/stop…  nginx / mysqld …
```

```bash
# 服务生命周期（最高频）
systemctl start nginx          # 启动（本次开机期间运行）
systemctl stop nginx           # 停止
systemctl restart nginx        # 重启（先 stop 再 start）
systemctl reload nginx         # 只重载配置，不重启进程（改完配置优先用它，不中断服务）
systemctl status nginx         # 查看状态（最常用的排查命令）

# 开机自启（和上面 start 是两回事，下面专门讲）
systemctl enable nginx         # 设置开机自启
systemctl disable nginx        # 取消开机自启
systemctl enable --now nginx   # 设开机自启 + 现在立刻启动（合二为一，最常用）

# 判断状态（写脚本时用，只输出一个词）
systemctl is-active nginx      # 现在是否运行中 → active / inactive
systemctl is-enabled nginx     # 是否开机自启 → enabled / disabled
```

> ⚠️ `reload` 不是所有服务都支持（主要是 nginx 等少数）。报 `Job type reload is not applicable` 就退回用 `restart`。

#### 最容易混的点：start/stop 和 enable/disable 是两件事

新手常以为"start 了开机就会自动起"——**不会**。这是**两个独立开关**：

| | 只管"现在这一次" | 只管"以后每次开机" |
|--|--|--|
| 开 | `start` | `enable` |
| 关 | `stop` | `disable` |

四种组合：

```bash
systemctl start nginx              # 现在跑，但重启电脑后不会自动起
systemctl enable nginx             # 现在不启动，但下次开机会自动起
systemctl enable --now nginx       # 现在就跑 + 开机也自动起 ✅ 装完服务一般用这条
systemctl disable --now nginx      # 现在就停 + 开机也不再起（彻底关掉，如防火墙）
```

> 记忆：**start/stop 管"当下"，enable/disable 管"未来开机"**。`--now` 的作用是"顺便把当下也办了"。

#### 服务名怎么知道？（软件名 ≠ 服务名）

命令最后那个名字不是随便写的，常见软件的服务名要记一下，**有的和软件名不一样**：

| 软件 | 服务名 | 说明 |
|------|--------|------|
| Nginx | `nginx` | 同名 |
| MySQL | `mysqld` | 注意多个 **d**（daemon 守护进程） |
| MariaDB | `mariadb` | — |
| Tomcat（第9节自建服务） | `tomcat` | 自己在 service 文件里定的名 |
| SSH | `sshd` | 多个 d |
| 防火墙 | `firewalld` | 多个 d |
| 定时任务 | `crond` | 多个 d |

> 规律：很多**系统自带的后台服务名都以 `d` 结尾**（daemon 守护进程），如 `sshd`/`crond`/`firewalld`/`mysqld`。拿不准就用下面的 list 命令搜，或按 Tab 补全。

```bash
systemctl list-units --type=service              # 列出所有已加载的服务，找名字
systemctl status mysql          # 名字写错时：Unit mysql.service could not be found.
systemctl status mysqld         # 换成 mysqld 就对了
```

#### status 输出怎么读（排查必看）

```bash
systemctl status nginx
```

```
● nginx.service - The nginx HTTP server
   Loaded: loaded (/usr/lib/systemd/system/nginx.service; enabled; ...)   ← ②开机自启？
   Active: active (running) since ...                                      ← ①现在在跑？
 Main PID: 1234 (nginx)                                                    ← ③主进程 PID
```

只盯两行就够：

| 行 | 看什么 | 正常 | 异常 |
|----|--------|------|------|
| **Active** | 现在的运行状态 | `active (running)` | `failed`（启动失败）/ `inactive`（没启动） |
| **Loaded** | 是否开机自启 | `enabled` | `disabled`（开机不起） |

启动失败时，status 下面还会打印最后几行报错；要看完整报错去 5.2 的 `journalctl -u 服务名`。

#### 两个新手必知

- **自己写的 .service 文件放哪？** 统一放 `/etc/systemd/system/`（第 9 节给 Tomcat 写服务就是放这里），不要动 `/usr/lib/systemd/system/` 里软件包自带的文件；
- **改完 service 文件必须 daemon-reload**：systemd 会把配置缓存到内存，新增或改过 `.service` 文件后要先 `systemctl daemon-reload` 让它重新扫描（只是 start/stop/reload 服务则不需要）。
- **普通用户执行可能要加 sudo**：`status` 普通用户能看，但 `start/stop/enable` 等改动操作一般需要 root 权限（`sudo systemctl start nginx`）。

#### 完整走一遍：从安装到能访问（以 nginx 为例）

```bash
sudo yum install -y nginx          # 1. 安装（第7章包管理讲 yum）
sudo systemctl enable --now nginx  # 2. 立刻启动 + 设开机自启
systemctl status nginx             # 3. 确认 active (running)
curl http://localhost              # 4. 验证能访问（80 端口）

sudo systemctl reload nginx        # 以后改完 /etc/nginx/nginx.conf：平滑重载
```

### 5.4 防火墙管理（firewalld）（必会）
> 🏷️ ⭐ 开发必会 —— 服务起不来、网页打不开，80% 是防火墙拦住了

CentOS 7 默认用 **firewalld** 管理端口放行（底层是 Linux 内核的 netfilter，不用深究）。装完服务第一件事就是放行端口，或者学习阶段直接关掉它。

**① 看状态和当前规则**

```bash
systemctl status firewalld            # 看防火墙服务是否 running
firewall-cmd --state                  # 更简洁：running / not running
firewall-cmd --list-all               # 最常用：一次看全开了哪些端口/服务
firewall-cmd --list-ports             # 只看端口
```

**② 开端口（部署 Web 服务、数据库必做）**

```bash
# 放行单个端口（--permanent 表示永久生效，不加重启后规则丢失）
firewall-cmd --add-port=80/tcp --permanent       # Web 服务
firewall-cmd --add-port=443/tcp --permanent      # HTTPS
firewall-cmd --add-port=8080/tcp --permanent     # Tomcat
firewall-cmd --add-port=3306/tcp --permanent     # MySQL（生产别直接对公网开！）

# 放行一段连续端口
firewall-cmd --add-port=30000-30999/tcp --permanent

# 也可以按服务名放行（语义更清晰）
firewall-cmd --add-service=http --permanent

# ⭐ 加完规则必须 reload，否则不生效
firewall-cmd --reload
firewall-cmd --list-ports             # 验证：能看到刚加的端口
```

> ⚠️ **`--permanent` 和 `--reload` 必须配对**：先 `--add-port ... --permanent`，再 `--reload`。少了第二步，规则没真正生效，从外部照样连不上。

**③ 移除端口**

```bash
firewall-cmd --remove-port=80/tcp --permanent
firewall-cmd --reload                 # 改完照样要 reload
```

**④ ⭐ 关闭防火墙（学习阶段最常用）**

自己虚拟机里学习时，每装一个服务（Nginx/Tomcat/MySQL）都要放行端口很烦，**直接关掉防火墙最省事**，装啥端口都通。这也是本课件所有实验默认的做法。

**关闭必须做两个动作**（对应 5.1 讲的两个独立开关，少一个都留尾巴）：

| 动作 | 命令 | 不管会怎样 |
|------|------|-----------|
| ① **现在立刻关掉** | `systemctl stop firewalld` | 不关：本次开机防火墙还在拦端口 |
| ② **禁止开机自启** | `systemctl disable firewalld` | 不禁：重启虚拟机后防火墙又自动起来了 |

```bash
# 方式1：两条分开写（看得清楚）
sudo systemctl stop firewalld       # 当前立刻停掉
sudo systemctl disable firewalld    # 开机也不要再启动

# 方式2：一行连写（&& = 前一条成功才执行后一条，效果一样）
sudo systemctl stop firewalld && sudo systemctl disable firewalld
```

执行后大概输出：

```
Removed symlink /etc/systemd/system/dbus-org.fedoraproject.FirewallD1.service.
Removed symlink /etc/systemd/system/basic.target.wants/firewalld.service.
# 这两行是 disable 删除开机自启的软链接，属正常提示，不是报错
```

**验证真的关干净了（两个状态都要确认）：**

```bash
# 方法1：看服务状态
sudo systemctl status firewalld
#   Active: inactive (dead)     ← 当前没在跑 ✅
#   Loaded: loaded (...; disabled)  ← 开机不自启 ✅

# 方法2：firewalld 自己的命令（最直接）
firewall-cmd --state
# not running                   ← 显示这个 = 防火墙已关 ✅
```

> 两个状态要**同时满足**：`inactive/dead`（当下关了）+ `disabled`（开机不起）。只 stop 没 disable，重启后防火墙会复活，你会发现"明明关过了，端口怎么又连不上了"。

**关完防火墙后：**

- 之前 ② 加的 `--add-port` 规则**不用管了**（防火墙都没了，规则无从生效），也不需要再 `--reload`；
- 现在 Nginx（80）、Tomcat（8080）、MySQL（3306）等端口从外部都能直接访问，可直接在 Windows 浏览器测试；
- 网络服务、SSH **不受影响**，不会因为关防火墙而断连（你正在用的 SSH 照常连着）。

**以后想重新打开防火墙**（比如练到端口放行、或要模拟真实服务器）：

```bash
sudo systemctl enable --now firewalld    # 立刻启动 + 恢复开机自启
firewall-cmd --state                     # running = 又开起来了
```

> ⚠️ **生产环境 / 云服务器严禁关防火墙！** 关闭等于把所有端口直接暴露在网络上，数据库等会被扫描攻击。正确做法是用 ② **精确放行需要的端口**，其余一律拦着。而且阿里云/腾讯云等**云服务器有两层**：系统里的 firewalld + 控制台的**安全组**，两边都要放行对应端口，外网才连得通。个人虚拟机学习可以关，上线绝不能关。

**⑤ firewall-cmd 速查表**

| 场景 | 命令 |
|------|------|
| 看所有规则 | `firewall-cmd --list-all` |
| 开 80 端口 | `firewall-cmd --add-port=80/tcp --permanent && firewall-cmd --reload` |
| 关 80 端口 | `firewall-cmd --remove-port=80/tcp --permanent && firewall-cmd --reload` |
| 学习机关闭防火墙 | `systemctl stop firewalld && systemctl disable firewalld` |
| 重新开启防火墙 | `systemctl enable --now firewalld` |

**⑥ 排查"服务起不来、连不上"的标准流程**

```bash
# 1. 服务自己起没起
systemctl status nginx              # 看 Active: active (running)

# 2. 端口有没有监听
ss -tlnp | grep :80                 # 应该看到 0.0.0.0:80 监听

# 3. 防火墙放没放行（最常被忽略！）
firewall-cmd --list-ports           # 看 80/tcp 在不在

# 4. 本机自己能不能访问
curl http://localhost              # 通了说明服务没问题，是防火墙的锅
```

> 💡 90% 的"端口连不上"：第 4 步本机通、远程不通，就是**防火墙的锅**——要么没 `--add-port`、要么忘了 `--reload`。

### 6.1 top — 进程动态监控（必会）
> 🏷️ ⭐ 开发必会 —— 最常用的"看系统有多忙"命令

```bash
# 启动 top（实时刷新，按 q 退出）
top
top -d 1            # 刷新间隔改成 1 秒（默认 3 秒）
top -p 1234,5678    # 只盯指定 PID 的进程
```

**top 里记住这几个键就够：**

| 按键 | 作用 |
|------|------|
| `q` | 退出 |
| `P` | 按 CPU 占用排序（默认） |
| `M` | 按内存占用排序 |
| `1` | 展开/折叠每个 CPU 核心的占用 |
| `k` | 杀进程（输入 PID 再输信号，等价于另开终端 kill）   不常用也不好用 |
| `u` | 只看某个用户的进程 |

**top 输出长这样：**

```
top - 10:30:00 up 5 days,  3:22,  2 users,  load average: 0.05, 0.10, 0.15
Tasks: 234 total,   1 running, 233 sleeping,   0 stopped,   0 zombie
%Cpu(s):  3.2 us,  1.0 sy,  0.0 ni, 95.0 id,  0.0 wa,  0.0 hi,  0.0 si,  0.0 st
KiB Mem :  8192000 total,  2048000 free,  3072000 used,  3072000 buff/cache
KiB Swap:  2048000 total,  2048000 free,        0 used.  4500000 avail Mem

  PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
 1234 mysql     20   0  892345  51234  12345 S   5.2  0.6   5:23.45 mysqld
```

下面**逐行逐字段**解释，一行都不跳过。

---

**第 1 行：系统整体状态**

```
top - 10:30:00 up 5 days,  3:22,  2 users,  load average: 0.05, 0.10, 0.15
 ↑     ↑          ↑              ↑          ↑
命令名  当前时间  已运行时长     当前登录用户数  平均负载
```

| 字段 | 含义 | 怎么看 |
|------|------|--------|
| `top` | 命令名，固定显示 | — |
| `10:30:00` | 当前系统时间 | 和 `date` 输出一致 |
| `up 5 days, 3:22` | 系统已连续运行 **5 天 3 小时 22 分** | 重启过就会变小；运维常看 uptime 判断稳定性 |
| `2 users` | 当前登录的用户数（开了几个终端/SSH 会话） | 多终端登录时会增加 |
| `load average: 0.05, 0.10, 0.15` | 最近 **1 分钟 / 5 分钟 / 15 分钟**的平均负载 | 见下方专门讲解 |

**load average 怎么判断（重点）**

> 🏷️ ⭐ 开发必会 —— 用"load ÷ 核数"这个比值判断，最直观

load 不是百分比，它是"正在用 CPU + 排队等 CPU/磁盘"的进程**数量**。三个值分别是 **1 分钟、5 分钟、15 分钟**的平均负载，**单独看，不加起来**。

```bash
nproc          # 先查你的 CPU 核数，比如 2
```

**怎么查 CPU 核数（必会）**

| 命令 | 输出 | 含义 |
|------|------|------|
| `nproc` | `2` | 最简单，直接输出**逻辑核数**（含超线程） |
| `lscpu` | 一大段信息 | 最详细，含物理核数、逻辑核数、CPU 型号、架构 |
| `cat /proc/cpuinfo \| grep processor \| wc -l` | `2` | 从 `/proc/cpuinfo` 数 processor 行数，等价于 `nproc` |
| `cat /proc/cpuinfo \| grep "cpu cores" \| uniq` | `cpu cores : 2` | **物理核心数**（不含超线程） |

**物理核 vs 逻辑核（容易混）**：

- **物理核（cpu cores）**：CPU 芯片上真实的核心数，比如 2 核
- **逻辑核（processor，nproc 输出）**：开了超线程后，1 个物理核变 2 个逻辑核（比如 2 物理核 → 4 逻辑核）；没开超线程则物理核=逻辑核
- **判断 load 用逻辑核（nproc 的值）**：因为操作系统调度是按逻辑核来的

**例子**：

```bash
nproc
# 输出 2（逻辑核数，判断 load 用这个）

lscpu | grep -E "CPU\(s\)|Thread|Core|Socket|On-line"
# CPU(s):                2     ← 逻辑核 = 2
# On-line CPU(s) list:   0,1   ← 在线的 CPU 编号是 0 和 1（两个核都在线）
# Thread(s) per core:    1     ← 每个物理核 1 线程（没开超线程）
# Core(s) per socket:    2     ← 物理核 = 2
# Socket(s):             1     ← 1 颗 CPU
# 结论：1 颗 CPU × 2 物理核 × 1 线程 = 2 逻辑核
```

| 字段 | 含义 |
|------|------|
| `CPU(s)` | 逻辑核数（判断 load 用这个） |
| `On-line CPU(s) list` | 在线的 CPU 编号（关机/热插拔可能有核离线，平时全在线） |
| `Thread(s) per core` | 每个物理核的线程数：1=没超线程，2=开了超线程 |
| `Core(s) per socket` | 每颗 CPU 的物理核数 |
| `Socket(s)` | CPU 颗数（服务器可能有多颗） |

> 💡 **日常只用 `nproc` 就够了**。`lscpu` 想看详细信息时再用。物理核数只有在做性能调优、绑核时才需要关心。

**核心公式：`CPU 繁忙程度 = load 值 ÷ CPU 核数`**

以你举的 `load average: 0.05, 0.10, 0.15` 为例，假设 2 核机器：

| 时间段 | load 值 | ÷ 2 核 | CPU 繁忙程度 | 结论 |
|--------|---------|--------|-------------|------|
| 1 分钟 | 0.05 | 2.5% | 几乎空闲 | ✅ 很好 |
| 5 分钟 | 0.10 | 5% | 几乎空闲 | ✅ 很好 |
| 15 分钟 | 0.15 | 7.5% | 几乎空闲 | ✅ 很好 |

> 💡 有人用"三个值加起来除以 3"算平均负载：(0.05+0.10+0.15)÷3=**0.10**。这是**民间粗略算法**——直接看平均值大小，0.10就是10%，远小于70%， 这就说明系统很闲。
>
> **严谨算法**是每个值**单独除以核数**：0.05÷2=2.5%、0.10÷2=5%、0.15÷2=7.5%，都远低于 100%，正常。因为三个时间段代表不同时间窗口的负载，且是否过载要和核数比。
>
> 两种算法结论一致（都很闲），日常用哪种都行，别混在一起算。

**通用判断表（以 2 核为例，其他核数同理换算）**：

| load 值（2 核） | load ÷ 核数 | 含义 | 怎么办 |
|-----------------|------------|------|--------|
| < 2 | < 100% | 正常，CPU 没满 | 不用管 |
| = 2 | = 100% | CPU 刚好用满 | 观察，看会不会持续 |
| 持续 2~4 | 100%~200% | 过载，有进程在排队等 CPU | 查 `ps aux --sort='-%cpu'` |
| 持续 > 4 | > 200% | 严重过载 | 立刻查占资源的进程 |

**趋势判断（比单个值更重要）**：

| 1 分钟 vs 15 分钟 | 含义 |
|-------------------|------|
| 1 分钟 > 15 分钟 | 负载在**上升**（刚出问题，赶紧查） |
| 1 分钟 < 15 分钟 | 负载在**下降**（问题在缓解，可以放心） |
| 三个值差不多 | 负载**稳定**，看绝对值判断即可 |

> 🔑 **一句话记忆**：**先 `nproc` 看核数，再用 `load ÷ 核数` 看繁忙程度，最后用 `1分钟 vs 15分钟` 看趋势**。比值 < 100% 正常，持续 > 100% 要查谁占 CPU。

---

**第 2 行：进程状态统计**

```
Tasks: 234 total,   1 running, 233 sleeping,   0 stopped,   0 zombie
 ↑      ↑              ↑            ↑             ↑           ↑
标签  总进程数      正在运行的     休眠中的        被停止的      僵尸进程
```

| 字段 | 含义 | 怎么看 |
|------|------|--------|
| `Tasks` | 标签，固定显示 | — |
| `234 total` | 当前**总进程数**（含运行、休眠、僵尸等所有状态） | 正常，机器上跑着各种后台服务 |
| `1 running` | **正在运行**（用着 CPU）的进程数 | 通常 1~3 个，机器闲时只有 top 自己在跑 |
| `233 sleeping` | **休眠中**（等事件、等数据，不占 CPU） | 绝大多数进程平时都在休眠，正常 |
| `0 stopped` | **被停止**（暂停）的进程 | 0 就好；按 Ctrl+Z 暂停的进程会出现在这 |
| `0 zombie` | **僵尸进程** | **必须为 0**！不为 0 说明有程序没正确回收子进程，要修代码 |

> 💡 什么是僵尸进程？程序 A 创建了子进程 B，B 退出后 A 没去"收尸"（没调用 wait()），B 就变成僵尸——占着 PID 但不占资源。一般过一会父进程处理了就消失；**持续存在才要管**，找对应的父进程修或重启服务。

---

**第 3 行：CPU 时间花在哪**

```
%Cpu(s):  3.2 us,  1.0 sy,  0.0 ni, 95.0 id,  0.0 wa,  0.0 hi,  0.0 si,  0.0 st
 ↑       ↑         ↑         ↑         ↑         ↑         ↑         ↑         ↑
标签   用户空间   内核空间   nice调整   空闲      IO等待    硬件中断   软件中断   虚拟化偷取
```

这是**所有 CPU 核心的平均**（加 `1` 键可展开每个核心单独看）。8 个字段全解释：

| 字段 | 全称 | 含义 | 偏高说明什么 |
|------|------|------|-------------|
| `us` | user | **用户程序**占用的 CPU 时间（你的 Java/Python/Go 代码） | 应用计算量大，去查业务进程的 %CPU |
| `sy` | system | **Linux 内核**占用的 CPU 时间（进程调度、内存管理、系统调用） | 频繁系统调用或大量进程/线程 |
| `ni` | nice | 被 nice 命令调整过优先级的进程占用 | 正常 0，调过优先级才会变 |
| `id` | idle | **CPU 空闲**比例 | 越高越闲；长期接近 0 → CPU 跑满了，要查 us 还是 sy |
| `wa` | iowait | **等磁盘 I/O** 消耗的时间 | **磁盘是瓶颈**！大量写日志、数据库查、拷贝文件时会高 |
| `hi` | hardware interrupt | **硬件中断**占用（网卡收包、磁盘完成、键盘输入） | 网络流量大或磁盘忙时会高 |
| `si` | software interrupt | **软件中断**占用（内核内部调度） | 一般很低 |
| `st` | steal | **虚拟化环境被偷走的时间**（宿主机抢了 CPU 给别的虚拟机） | 0 正常；非 0 说明虚拟机分到的 CPU 不够用 |

> 💡 **重点盯 4 个**：`us`（应用）、`sy`（内核）、`id`（空闲）、`wa`（IO）。`ni`/`hi`/`si`/`st` 开发很少调，知道含义就行。
>
> 怎么读：`id 95.0` 说明 CPU 95% 时间在闲着，`us 3.2` 你的 Java 代码占了 3.2%，`sy 1.0` 内核占了 1%，**机器很闲**。如果哪天 `wa 40.0`，就是磁盘在卡。
>
> 磁盘中断占用，就是磁盘完成读写之后，发硬件中断（IRQ）通知 CPU，CPU 停下手上任务、在内核态处理这次磁盘中断所消耗的 CPU 时间

---

**第 4 行：物理内存**

```
KiB Mem :  8192000 total,  2048000 free,  3072000 used,  3072000 buff/cache
 ↑         ↑              ↑              ↑              ↑
单位      总内存          完全空闲        被程序占用       缓冲+缓存
```

| 字段 | 含义 | 怎么看 |
|------|------|--------|
| `KiB Mem` | 标签 + 单位（KB） | CentOS 7 用 KiB，Ubuntu 有时用 MiB |
| `8192000 total` | 总物理内存（8GB） | 机器装了多少就是多少 |
| `2048000 free` | **完全空闲、没被用**的内存 | 通常很小，别慌——Linux 故意留很少 |
| `3072000 used` | 被进程**实际占用**的内存 | 含缓存？不，缓存算在 buff/cache 里 |
| `3072000 buff/cache` | **buff（缓冲）+ cache（缓存）** | 系统拿空闲内存做磁盘缓存，要给应用用时会**自动释放** |

> 💡 **关键认知**：Linux 的 `free` 小不代表内存不够！系统会把闲内存全拿去做缓存加速磁盘 IO，应用要时自动还。**别看到 free 2000000（2G）就想加内存**。

---

**第 5 行：交换空间 + 真正可用内存**

```
KiB Swap:  2048000 total,  2048000 free,        0 used.  4500000 avail Mem
 ↑           ↑              ↑              ↑           ↑
单位+标签   Swap总量       Swap空闲      Swap已用      真正能用的内存
```

| 字段 | 含义 | 怎么看 |
|------|------|--------|
| `KiB Swap` | 标签 + 单位（KB） | — |
| `2048000 total` | **Swap 总量**（磁盘上划出来当内存用的空间） | 一般设为物理内存的 1~2 倍 |
| `2048000 free` | Swap 里还没被用的部分 | 和 total 一样就是没用到 Swap |
| `0 used` | Swap **已用**了多少 | **0 最好**；持续非 0 说明物理内存不够、开始把东西挤到磁盘上了，**Swap 比内存慢几百倍** |
| `4500000 avail Mem` | **应用真正还能用的内存**（free + 可回收的 buff/cache） | **只盯这一个数**！它告诉你"现在还能给新程序多少内存" |

> 💡 综合判断内存：**avail Mem 够 → 没问题**；Swap used 持续增长 → 内存不够了；`free -h` 命令能更直观地看（-h 人类可读单位）。

**进程表头行：每列什么意思**

```
  PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
  ↑    ↑         ↑   ↑      ↑       ↑       ↑   ↑    ↑     ↑       ↑       ↑
 进程 所属用户  优先  nice  虚拟   物理   共享 状态 CPU%  MEM%   CPU累计  命令名
  ID            级   值    内存   内存   内存       占比  占比   运行时间
```

进程示例行：
```
 1234 mysql     20   0  892345  51234  12345 S   5.2  0.6   5:23.45 mysqld
```

| 列 | 全称 | 含义 | 怎么看 |
|----|------|------|--------|
| **PID** | Process ID | 进程 ID，唯一的数字身份证 | kill/pkill 就靠这个定位 |
| **USER** | 所属用户 | 谁启动的这个进程 | root 启动的是系统服务，mysql 启动的是 mysqld |
| **PR** | Priority | 内核给的**动态优先级**，值越小越优先被 CPU 执行 | 一般都是 20，不用调 |
| **NI** | Nice | 用户可以设置的**优先级偏移量**，-20（最高）到 19（最低） | 普通进程都是 0；`nice -n 5 命令` 启动会让进程更"谦让" |
| **VIRT** | Virtual | **虚拟内存**大小（进程申请过的总内存，不是真实占用） | 通常很大，**不代表真实用了这么多**，不用太在意 |
| **RES** | Resident | **真实占用的物理内存**（驻留内存） | **排查内存问题看它**，单位 KB；加 `%MEM` 一起看更直观 |
| **SHR** | Shared | **共享内存**（和其他进程共享的代码段/库，如 libc.so） | RES - SHR ≈ 进程独占的物理内存 |
| **S** | Status | **进程状态** | R=运行中、S=休眠、D=磁盘IO等待（不可杀）、Z=僵尸、T=被停止（见 1.3 节 STAT 表） |
| **%CPU** | CPU usage | 从上次刷新到现在，这个进程占了多少 CPU | 排序后看哪个最高（top 默认就是按 CPU 排序） |
| **%MEM** | Memory usage | 占总物理内存的百分比 | 和 RES 一起看，Java 应用 20%~50% 正常 |
| **TIME+** | CPU time | 这个进程**累计花了多少 CPU 时间**（不是运行时长） | `5:23.45` = 5 分 23 秒；CPU 密集型进程会涨得很快 |
| **COMMAND** | 启动命令 | 进程是被谁启动的 | 有时会被截断，`top -c` 可显示完整命令行 |

#### 开发到底看哪些列？一张图告诉你重点

12 列不用全看，分三档：

| 档位 | 列 | 为什么 | 怎么用 |
|------|-----|--------|--------|
| ⭐⭐⭐ **必看** | **PID** | 杀进程要用 | 看到异常进程，记下 PID → `kill PID` |
| ⭐⭐⭐ **必看** | **%CPU** | 谁在烧 CPU | 排序后看哪个进程占用最高（按 `P` 键按 CPU 排序） |
| ⭐⭐⭐ **必看** | **%MEM** | 谁在吃内存 | 排序后看哪个进程占用最高（按 `M` 键按内存排序） |
| ⭐⭐⭐ **必看** | **COMMAND** | 知道这进程是啥 | 不认识就 Google 一下进程名 |
| ⭐⭐ **经常看** | **RES** | 进程真实占的物理内存 | Java 进程 RES 飙到 4G = 堆配大了，要调 -Xmx |
| ⭐⭐ **经常看** | **S** | 进程状态 | Z 多 = 有 bug；D 多 = 磁盘卡 |
| ⭐ **偶尔看** | **USER** | 进程是谁跑的 | 用 root 跑应用是安全隐患，要切专用用户 |
| ⭐ **偶尔看** | **TIME+** | 累计占 CPU 多久 | 排查"这程序跑了半天到底消耗多少 CPU" |
| ❌ **开发不用管** | **PR** | 内核优先级，改不了 | 内核调度的事，你看也没用 |
| ❌ **开发不用管** | **NI** | nice 值，优先级调整 | 开发岗极少用 renice 调优先级 |
| ❌ **开发不用管** | **VIRT** | 虚拟内存（含申请没用的） | Java VIRT 几十 G 是正常的，看 RES 才准 |
| ❌ **开发不用管** | **SHR** | 共享内存 | 内核/库共享部分，开发用不上 |

**口诀：PID + %CPU + %MEM + COMMAND 必看，RES + S 经常看，其他不用管。**

> 💡 **实战速查**：
> - 机器卡 → 按 `P` 看 %CPU 谁最高 → 按 `M` 看 %MEM 谁最高
> - 进程起不来 → 找 PID → `kill PID` 重启
> - Java 慢 → 找 COMMAND 含 java 的 → 看 RES 是不是堆太大

**⑤ htop——top 的直观增强版（推荐装上）**

```bash
sudo yum install -y epel-release && sudo yum install -y htop   # 需要 EPEL 扩展源（源失效先按 7.1.0 修）
htop
```

相比 top：鼠标能点、彩色柱状图直观、F5 树状视图、F9 直接发信号杀进程，`q` 退出。日常有 top + htop 完全够用。

### 6.2 free — 内存状态（必会）
> 🏷️ ⭐ 开发必会 —— 一条命令看内存还剩多少

```bash
free -h              # 人类可读单位（GB/MB），最常用
free -h -s 1         # 每 1 秒刷新一次，Ctrl+C 退出
```

输出里重点看两列：
- **available**：应用实际还能用的内存（含可回收缓存），低于总内存 20% 就要注意
- **Swap 的 used**：交换分区被持续占用，说明物理内存不够用了

### 6.3 ss / netstat — 查端口占用（必会）
> 🏷️ ⭐ 开发必会 —— 部署服务后确认"端口起来没有"，排查"端口被谁占了"

```bash
sudo ss -tlnp                        # ⭐ 最高频：看所有正在监听的 TCP 端口和对应进程
sudo ss -tlnp | grep :8080           # Tomcat 起没起、8080 被谁占了
sudo netstat -tlnp | grep :80        # 老命令，作用相同（需 yum install net-tools）
sudo ss -s                           # 当前连接数量汇总
sudo lsof -i :80                     # 查 80 端口被哪个进程占用（另一种写法）
```

> 💡不加sudo，很多都看不到， `-t` TCP、`-l` 只看监听中、`-n` 显示数字端口不反查域名（快）、`-p` 显示进程名。记不住参数没关系，`ss -tlnp | grep 端口号` 这一条覆盖 90% 场景。

**输出各列含义（必会）**：

```
State   Recv-Q  Send-Q  Local Address:Port     Peer Address:Port
LISTEN  0       128     *:80                    *:*
LISTEN  0       128     127.0.0.1:631           *:*
LISTEN  0       128     192.168.122.1:53        *:*
LISTEN  0       128     [::]:80                 [::]:*
```

| 列 | 含义 |
|----|------|
| `State` | 连接状态，`LISTEN` = 正在监听（服务在跑） |
| `Recv-Q` / `Send-Q` | 接收/发送队列积压字节数，正常都是 0 |
| `Local Address:Port` | **本机监听的地址:端口** |
| `Peer Address:Port` | 对端地址，监听状态下都是 `*:*`（还没连进来） |

**Local Address 里的 `*` / `0.0.0.0` / `127.0.0.1` / 具体 IP 是什么意思（重点）**：

| 监听地址 | 含义 | 谁能连进来 | 安全等级 |
|----------|------|-----------|---------|
| `*:80` 或 `0.0.0.0:80` | 监听**所有网卡**的 80 端口 | 本机 + 外部机器都能连 | ⚠️ 对外暴露 |
| `[::]:80` | 监听所有 **IPv6** 地址的 80 端口 | IPv6 网络可达的机器 | ⚠️ 对外暴露 |
| `127.0.0.1:631` | 只监听**本机回环** | **只有本机能连**，外部连不进来 | ✅ 安全 |
| `192.168.122.1:53` | 只监听**指定网卡**的 IP | 只有该网段能连 | 视情况 |

> 🔑 **判断服务安不安全，就看 Local Address**：
> - 是 `*` 或 `0.0.0.0` → 对外暴露，要靠防火墙挡
> - 是 `127.0.0.1` → 只本机可用，最安全（数据库推荐这样配）

**端口号不一定是默认值（必会）**：

服务的端口是配置文件决定的，不一定是你记得的"默认值"。比如：

| 服务 | 默认端口 | 你机器上实际可能是 |
|------|---------|------------------|
| MySQL | 3306 | **3307**（MariaDB 或改了配置） |
| Redis | 6379 | **6380**（多实例或改了配置） |
| SSH | 22 | 2222（安全加固改的） |
| Nginx | 80 | 8080（非 root 启动或多站点） |

**怎么确认服务用了哪个端口**：

```bash
# 方法 1：看进程名（比如找 mysql）
ss -tlnp | grep -i mysql
# 输出可能是：*:3307  ← 原来监听 3307 不是 3306

# 方法 2：看配置文件
grep -i port /etc/my.cnf           # MySQL
grep -i port /etc/redis.conf       # Redis
```

> 💡 **排错经验**：连不上数据库时，先 `ss -tlnp | grep mysql` 确认它到底监听哪个端口，别默认就是 3306。截图里 MySQL 监听的是 `*:3307`，连接时要用 3307。

### 6.4 df — 磁盘空间（必会）
> 🏷️ ⭐ 开发必会 —— 磁盘满了服务会挂，上线前必查

```bash
df -h              # ⭐ 最常用：人类可读单位（GB/MB），一眼看各分区用了多少
df -hT             # -T 额外显示文件系统类型（xfs/ext4）
```

**输出怎么看：**

```
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        50G   15G   35G  30% /          ← 系统盘，30% 使用率
/dev/sdb1       500G  450G   50G  90% /data        ← 数据盘，90% 了！快满了
tmpfs           3.9G     0  3.9G   0% /dev/shm
```

| 重点看 | 含义 | 怎么看 |
|--------|------|--------|
| **Use%** | 使用率 | **超过 80% 就要注意**，超过 90% 赶紧清理 |
| **Avail** | 剩余可用空间（不是 Used） | 别用 Used 判断，看 Avail 还剩多少 |
| **Mounted on** | 挂载点 | `/` 是系统盘，`/data` 是数据盘，`/tmp` 是临时目录 |

> 💡 **常见满盘原因**：日志没轮转（`/var/log/` 下 `messages` 或 nginx access.log 涨到几十 G）、core dump、临时文件没清。先 `du -sh /var/log/*` 找最大的文件再删。

### 6.5 iostat — 磁盘 IO 速率（了解即可）
> 🏷️ 开发排查磁盘性能时用，不是日常高频

`iostat` 能看磁盘**读写速度、IOPS、等待时间**——top 里 `wa`（IO 等待）高了，就用它确认是不是磁盘瓶颈。

```bash
# 安装（CentOS 7 默认没装，属于 sysstat 包）
sudo yum install -y sysstat

# 最常用：看磁盘设备的实时读写
iostat -x 1                    # -x 扩展信息（含速率、IOPS），1 秒刷新一次，Ctrl+C 退出
iostat -x sda                  # 只看 sda 这块盘
```

**输出重点看：**

| 字段 | 含义 | 怎么看 |
|------|------|--------|
| `r/s` / `w/s` | 每秒读/写请求数（IOPS） | 数据库高峰期会高 |
| `rkB/s` / `wkB/s` | 每秒读/写多少 KB（带宽） | 机械盘读 100~200MB/s，固态 300~1000MB/s |
| `%util` | 磁盘设备繁忙程度 | **接近 100% = 磁盘是瓶颈**，和 top 里的 `wa` 对应 |
| `await` | 平均等待时间（毫秒） | 机械盘 > 10ms 就慢了，固态一般 < 1ms |

> 💡 开发什么时候会用到？top 里看到 `wa 40%` 不知道是不是磁盘问题 → `iostat -x 1` 看 `%util` 是否接近 100%。是 → 磁盘瓶颈，要么换 SSD 要么减少并发 IO。

### 6.6 sar — 网络流量（了解即可）
> 🏷️ 开发排查网络问题时用，不是日常高频

`sar`（System Activity Reporter）能看**网卡收发速率**——怀疑网络慢、带宽不够时用。和 iostat 同属 sysstat 包。

```bash
# 安装（和 iostat 一起装过就不用了）
sudo yum install -y sysstat

# 最常用：看网卡实时流量
sar -n DEV 1                    # -n DEV 网络设备，1 秒刷新一次
sar -n DEV 1 eth0               # 只看 eth0 这块网卡
```

**输出重点看：**

```
IFACE   rxpck/s   txpck/s   rxkB/s   txkB/s   %ifutil
eth0     500.00    300.00    50.00    30.00    5.00
```

| 字段 | 含义 | 怎么看 |
|------|------|--------|
| `rxkB/s` | 每秒接收多少 KB（下载） | 几百 KB/s 正常，MB 级别就是大流量 |
| `txkB/s` | 每秒发送多少 KB（上传） | 同上 |
| `%ifutil` | 网卡利用率 | **接近 100% = 带宽跑满了** |

> 💡 开发什么时候会用到？接口慢怀疑是网络带宽不够 → `sar -n DEV 1` 看 txkB/s/rxkB/s 有没有跑满网卡带宽。1Gbps 网卡理论上限约 125MB/s（1000/8）。

## 7. 软件包管理（必会）
> 🏷️ ⭐ 开发必会 —— 装软件、查软件、卸载软件，全靠 yum

**① 先说清楚：装软件用什么**

CentOS 下装软件一律用 **YUM**：自动下载、自动解决依赖，一条命令装完。底层的 `rpm` 命令不处理依赖（缺依赖直接报错），**不要用它装软件**，只需会用它做两个查询：

```bash
rpm -qa | grep mysql        # 查某个包装没装过、什么版本（比 yum list 快）
rpm -qf /usr/bin/java       # 查某个文件是哪个包装进来的（rpm 独有）
```

> 💡 关系一句话：**yum 是 rpm 的智能前台**——yum 底层还是调 rpm 干活，只是帮你想清楚了"依赖装哪些、去哪个仓库下"。

### 7.1 YUM 包管理器（必会）
> 🏷️ ⭐ 开发必会 —— 软件开发日常高频使用，务必掌握

#### ⚠️ 7.1.0 CentOS 7 用户必做：先修复 yum 源（否则装什么都报错）

CentOS 7 已于 **2024 年 6 月 30 日停止维护**，官方源服务器 `mirrorlist.centos.org` 已下线。新装的 CentOS 7.6 执行 `yum install` 大概率报：

```
Could not retrieve mirrorlist ... Could not resolve host: mirrorlist.centos.org
Cannot find a valid baseurl for repo: base/7/x86_64
```

**这不是你网络坏了，是源地址失效了。** 解决办法：把源地址改成国内镜像站的"归档仓库"（vault，只读的历史最终版，包很全，只是不再更新）。复制下面整段执行一次即可（推荐阿里云，国内最快）：

```bash
# 1. 先备份原来的源配置（出问题可还原）
sudo cp /etc/yum.repos.d/CentOS-Base.repo /etc/yum.repos.d/CentOS-Base.repo.bak

# 2. 注释掉失效的 mirrorlist，把 baseurl 改指向阿里云的归档地址
sudo sed -i -e 's|^mirrorlist=|#mirrorlist=|g' \
            -e 's|^#baseurl=http://mirror.centos.org/centos|baseurl=https://mirrors.aliyun.com/centos-vault|g' \
            /etc/yum.repos.d/CentOS-Base.repo

# 3. 地址里的 $releasever 是 7，而归档目录按最终版本号 7.9.2009 存放，替换掉
sudo sed -i 's|\$releasever|7.9.2009|g' /etc/yum.repos.d/CentOS-Base.repo

# 4. 清旧缓存、重建缓存
sudo yum clean all && sudo yum makecache
```

验证：`yum repolist` 能列出 base/extras/updates 三个源（共 1 万多个包），或直接试装 `sudo yum install -y wget`，能下载就是成功。7.6 装 7.9.2009 归档里的包完全兼容（同属 CentOS 7，小版本之间包通用）。

> 提示：改完源后课件后面所有 `yum install` 命令就都能正常用了。若想还原：`sudo cp /etc/yum.repos.d/CentOS-Base.repo.bak /etc/yum.repos.d/CentOS-Base.repo`。

**EPEL 扩展源也要同样处理（装 nginx / redis / htop 等官方源里没有的软件时才需要）：**

> ⚠️ **顺序很重要：先写好 repo 文件，再装 epel-release。** 因为如果系统里已残留一个失效的 `epel.repo`，yum 在执行**任何** install（包括装 epel-release 自己）前都会先检查所有源，一旦发现 epel 源失效就直接报 `Cannot find a valid baseurl for repo: epel` 整体失败——你会连"装包"这步都走不到。先覆盖写文件能同时兼容"已装过"和"没装过"两种情况。

```bash
# 第 1 步：先直接写好 epel.repo（没有会新建，已有坏的会覆盖），指向阿里云 epel-archive
#   先用 gpgcheck=0 兜底（此时 epel-release 可能还没装、密钥文件不一定在）
#   ⚠️ 注意：不能用 sudo cat > 文件，sudo 只对 cat 生效，重定向 > 是当前 shell 做的（普通用户），
#           会报"权限不够"。必须用 sudo tee，tee 以 root 身份写文件。
sudo tee /etc/yum.repos.d/epel.repo > /dev/null << 'EOF'
[epel]
name=EPEL 7 - $basearch
baseurl=https://mirrors.aliyun.com/epel-archive/7/$basearch/
enabled=1
gpgcheck=0
EOF

# 第 2 步：重建缓存（现在坏源已被替换，yum 能正常工作）
sudo yum clean all && sudo yum makecache

# 第 3 步：确认/补装 epel-release（已装会提示 already installed，属正常）
rpm -q epel-release || sudo yum install -y epel-release

# 第 4 步：验证，列表里出现 epel 一行（带包数量）= 成功
sudo yum repolist
```

> ✅ 想要更规范：第 3 步装好 epel-release 后密钥文件 `/etc/pki/rpm-gpg/RPM-GPG-KEY-EPEL-7` 就存在了，可把 repo 里 `gpgcheck=0` 改回 `1` 并加一行 `gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-EPEL-7`，再 `yum makecache`。学习环境保持 `0` 也不影响使用。
>
> 📌 报错对照：`Cannot find a valid baseurl for repo: epel` = epel 源失效/没按上面修；`No package nginx available` = 还没有 epel 源。

#### 7.1.1 yum 常用命令

```bash
# 基本用法
sudo yum install -y nginx        # 安装（-y = 安装过程的询问全部自动回答 yes）
yum remove nginx            # 卸载
yum check-update            # 检查可更新的包

# 查询
yum list installed          # 看已安装的包
yum search nginx            # 按名字搜索包
yum provides '*/ifconfig'   # 不知道某个命令在哪个包里时用这个查

# 仓库管理
yum repolist                # 列出当前生效的仓库（7.1.0 修源后用它验证）
yum clean all               # 清理缓存
yum makecache               # 重新生成缓存（改完源必做）
```

**场景速查：**

| 场景 | 命令 |
|------|------|
| 装一个软件 | `sudo yum install -y nginx` |
| 不知道命令在哪个包里（ifconfig 找不到时） | `yum provides '*/ifconfig'` 查到后装对应包 |
| 确认装过没有、什么版本 | `rpm -qa \| grep nginx` |
| 卸载软件 | `yum remove -y nginx` |
| 想装的东西源里没有 → 装 EPEL 扩展源 | `sudo yum install -y epel-release`（修源见 7.1.0） |
| 改完源配置后不生效 | `yum clean all && yum makecache` |

**常见坑：**

```bash
# 坑1：Another app is currently holding the yum lock（yum 锁被占用）
# 原因：上一个 yum 还没跑完（或自动更新进程在跑），yum 同一时刻只能运行一个
ps aux | grep -v grep | grep yum     # 看是谁占着
# 等它跑完即可；确认卡死了才 kill 掉对应进程

# 坑2：装完命令却找不到（如装了 net-tools，ifconfig 还是提示 command not found）
# 原因：PATH 没刷新或根本没装上，先确认再排查
rpm -qa | grep net-tools             # 先确认装上了没
yum provides '*/ifconfig'            # 装上还找不到就查命令到底在哪个包

# 坑3：报 Could not resolve host（源地址失效，CentOS 7 最常见）
# 解决：按 7.1.0 修源，一次搞定
```

### 7.2 RPM 包管理器（必会，配合 yum 用）
> 🏷️ ⭐ 开发必会 —— rpm 是 yum 的底层，**不处理依赖**，只在特定场景用

**rpm 和 yum 的关系一句话：yum 是 rpm 的"智能前台"**

| | RPM | YUM |
|---|---|---|
| 是什么 | Red Hat Package Manager，底层包管理工具 | 基于 rpm 的"智能前台"，帮你解决依赖 |
| 装软件 | ❌ 不处理依赖，缺包直接报错退出 | ✅ 自动查依赖、自动下载、一条命令装完 |
| 卸载 | ❌ 不检查依赖关系，可能把别的包依赖的东西删了 | ✅ 检查依赖，提示"xx 依赖它，不能删" |
| 唯一优势 | ✅ 能做 yum 做不到的 3 件事（见下） | 没有 |
| 开发日常 | **优先 yum，只在以下 3 种情况用 rpm** | 99% 的时候用 yum |

**只用 rpm 的 3 种情况（yum 做不到）：**

| 情况 | 命令 | 为什么 yum 做不到 |
|------|------|------------------|
| ① 查文件属于哪个包 | `rpm -qf /usr/bin/java` | yum 没有查文件归属的功能 |
| ② 装 .rpm 结尾的仓库配置包 | `rpm -Uvh mysql-community-release.rpm` | 这种包本身就是"配置文件"，装完才能用 yum 装软件 |
| ③ 导入 GPG 密钥 | `rpm --import 密钥地址` | yum 本身不管理密钥，只能靠 rpm 导入（本文档 MySQL 安装步骤里就用到了：`rpm --import https://repo.mysql.com/RPM-GPG-KEY-mysql-2022`） |

**rpm 必须会的 3 件事：**

```bash
# ① 查文件属于哪个包（yum 做不到）
rpm -qf /usr/bin/java                    # 查 java 命令是哪个包装进来的
rpm -qf $(which nginx)                   # 查 nginx 二进制来自哪个包

# ② 装 .rpm 结尾的仓库配置包（MySQL、Remi 源都用这种方式装）
#    注意：这里装的不是"软件本身"，而是"往 /etc/yum.repos.d/ 放一个仓库配置文件"
sudo rpm -Uvh https://dev.mysql.com/get/mysql57-community-release-el7-11.noarch.rpm
#    装完才会 /etc/yum.repos.d/ 里多一个 mysql-community.repo，然后才能 yum install mysql

# ③ 导入 GPG 密钥（装上面那个源包后，yum 才能信任它）
sudo rpm --import https://repo.mysql.com/RPM-GPG-KEY-mysql-2022
```

**rpm 完整命令速查（开发只用这几个）：**

> 📌 **`-q` = query 查询模式**，后面跟不同字母决定"查什么"：
> - **a** = all（所有）→ 列出所有已装的包
> - **i** = info（信息）→ 查某个包的详细信息
> - **f** = file（文件）→ 查某个文件属于哪个包

```bash
# 查询（最常用）
rpm -qa | grep nginx        # -qa：a=all，列出所有已装包，grep 过滤出 nginx
rpm -qi nginx               # -qi：i=info，查 nginx 包的详细信息（版本、发布时间、描述）
rpm -qf /usr/bin/java       # -qf：f=file，查 /usr/bin/java 这个文件是哪个包装进来的（rpm 独有）

# 安装 / 升级（只在装 .rpm 仓库配置包时用，装软件一律 yum）
sudo rpm -Uvh xxx.rpm       # 安装或升级（U=升级，没有就装；v=显示过程；h=进度条）
sudo rpm -ivh xxx.rpm       # 只安装（已有会报错）

# 卸载（不常用，yum remove 更安全）
sudo rpm -ev nginx          # 卸载（-e = erase，不检查依赖）

# GPG 密钥
sudo rpm --import 密钥地址   # 导入 GPG 密钥（yum 信任某源前必须做）
rpm -qa gpg-pubkey           # 查看已导入的密钥
```

> 📌 **什么是 GPG 密钥？为什么要导入？**
>
> **简单说：GPG 密钥 = 软件源的"身份证"，用来验证软件包是不是官方发布的，防止被篡改/植入木马。**
>
> 你添加了一个新的软件源（比如 MySQL 官方源），yum 从这个源下载软件包时，需要确认：
> - 这个包**确实是 MySQL 官方发的**，不是中间人篡改过的
> - 包**没有被植入木马或后门**
>
> 怎么验证？软件源在发布每个包时，会用自己的**私钥**给包签名；你导入的是它的**公钥**。yum 下载包后用公钥验证签名，验证通过才安装。
>
> **不导入会怎样？** yum 会报 `GPG key retrieval failed` 或 `Package is not signed`，拒绝安装。
>
> **类比**：就像快递签收要核对身份证，GPG 公钥就是软件源的"身份证复印件"，你先存一份，以后收"快递"（软件包）时核对。

> ⚠️ **rpm vs yum 的坑**：`rpm -Uvh xxx.rpm` 不等于"装软件"——它装的是"仓库配置包"，目的是往 `/etc/yum.repos.d/` 里写一个 `.repo` 文件，让 yum 知道去哪里下载真正的软件。真正装 MySQL 还是靠后面的 `yum install -y mysql-community-server`。

## 7.3 环境变量（开发必会）
> 🏷️ ⭐ 开发必会 —— 装完软件命令找不到、Java 找不到 JDK，90% 是环境变量问题

环境变量是什么？一句话：**给系统/进程看的"全局配置项"**，比如 `PATH` 告诉系统"去哪些目录找命令"，`JAVA_HOME` 告诉程序"JDK 装在哪"。

开发只需掌握 3 件事：**查变量、临时设置、永久设置**。

### 7.3.1 查环境变量
> 🎯 **作用**：装完软件命令找不到时，先查变量对不对——`command not found` 90% 是 PATH 里没那个目录，或 JAVA_HOME 根本没设。

```bash
# 看所有环境变量
env

# 看某个变量（最常用）
echo $PATH              # PATH 是最关键的，系统按这里面的目录顺序找命令
echo $JAVA_HOME         # 查 JDK 装在哪
echo $VIRTUAL_ENV       # 查当前 Python 虚拟环境路径（激活了才会有值）

# 更简洁，没装时输出空
echo $HOME              # 当前用户家目录
```

### 7.3.2 PATH：命令查找路径（必会）
> 🎯 **作用**：理解 PATH 你就明白"为什么装了软件却提示 command not found"——系统找不到命令，就是因为命令所在目录不在 PATH 里。

你敲 `java` 时，系统会按 `PATH` 里的目录**从左到右**挨个找有没有叫 `java` 的可执行文件。找到就执行，找不到就报 `command not found`。

```bash
# 看当前 PATH
echo $PATH
# /usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/root/bin
# 用冒号 : 分隔，从左到右依次查找

# 临时把某个目录加进 PATH（只对当前终端生效，关了就没）
export PATH=/usr/local/java/jdk8/bin:$PATH
# ↑ 注意是 $PATH 不是 PATH，要把原来的 PATH 拼到后面，否则原来的目录全丢了

# Python 场景：激活虚拟环境后，虚拟环境的 bin 目录会自动加到 PATH 最前面
source ~/env36/bin/activate
which python3            # 输出 /root/env36/bin/python3（不是系统的）
```

> 💡 **PATH 顺序很重要**：如果两个目录里都有 `java`，**左边的优先**。装了多个 JDK 时，PATH 写在前面的那个会被用。

### 7.3.3 临时设置（当前终端）
> 🎯 **作用**：只想在**当前这个终端窗口**临时用一下某个环境变量，不想影响其他终端、也不想永久保存。比如：测试一个新 JDK 版本好不好用、临时跑个需要特殊变量的脚本。

```bash
export JAVA_HOME=/usr/local/java/jdk8
export PATH=$JAVA_HOME/bin:$PATH

# 验证
java -version          # 能输出版本号就说明 PATH 配对了
echo $JAVA_HOME        # 输出 /usr/local/java/jdk8

# ── Python 场景：创建并临时激活虚拟环境 ──

# 第 1 步：确认宿主机装了 python3（CentOS 7 自带 python3 或 yum install -y python3）
python3 --version        # 输出 Python 3.x.x，有版本号说明装好了

# 第 2 步：用 venv 模块在家目录下创建虚拟环境 env36
# -m venv：以模块方式运行 venv（Python 自带的虚拟环境工具，不用额外装）
# ~/env36：虚拟环境的安装路径（家目录下的 env36 文件夹）
python3 -m venv ~/env36

# 第 3 步：激活虚拟环境（source 执行 activate 脚本，激活后提示符前会多 (env36)）
source ~/env36/bin/activate
python3 --version        # 验证用的是虚拟环境的 Python
which python3            # 验证路径指向 ~/env36/bin/python3（不是系统的 /usr/bin/python3）
echo $VIRTUAL_ENV        # 输出 /root/env36（激活后才有值，没激活是空的）

# 第 4 步：退出虚拟环境
deactivate
```

> ⚠️ 临时设置**只对当前 SSH 会话生效**，关掉终端或重新登录就没了。想永久生效必须写配置文件（7.3.4）。

### 7.3.4 永久设置（必会）
> 🎯 **作用**：让环境变量**每次开机/登录都自动生效**，不用每次开终端都敲一遍 export。比如 JDK 装好了，希望所有用户都能用 `java` 命令，就配到这里。

**推荐写法：写到 `/etc/profile.d/xxx.sh`**——所有用户登录时自动加载，不污染系统主配置文件。

```bash
# 新建一个脚本文件（文件名随意，以 .sh 结尾）
vim /etc/profile.d/java_env.sh

# 写入内容：
export JAVA_HOME=/usr/local/java/jdk8
export PATH=$JAVA_HOME/bin:$PATH
```

**让配置立即生效**（不用重新登录）：

```bash
source /etc/profile.d/java_env.sh
# 或者
. /etc/profile.d/java_env.sh
```

**验证**：

```bash
echo $JAVA_HOME    # 输出 /usr/local/java/jdk8
which java         # 输出 /usr/local/java/jdk8/bin/java
java -version      # 输出版本号
```

**Python 场景：把虚拟环境永久加到 PATH（了解，一般不这么用）**

> ⚠️ **为什么不推荐？** 一台服务器上通常有多个项目，每个项目有自己的虚拟环境（依赖版本不同）。如果永久把某个虚拟环境加到 PATH，所有用户、所有终端都只能用这一个环境，不同项目的依赖会冲突。所以一般用 `source activate` 临时激活（每个终端可以激活不同的环境，互不干扰）。

只有"整台机器就一个 Python 项目、所有人共用同一个环境"时，才考虑永久加到 PATH：

```bash
vim /etc/profile.d/python_env.sh

# 写入：
export VIRTUAL_ENV=/www/myproject/venv
export PATH=$VIRTUAL_ENV/bin:$PATH
```

```bash
source /etc/profile.d/python_env.sh
which python3    # 输出 /www/myproject/venv/bin/python3
```

> 💡 **日常 99% 的情况**：不用全局配虚拟环境，而是 `source ~/env36/bin/activate` 临时激活。生产部署 Django 时，在 systemd 的 `ExecStart` 里直接写虚拟环境 python 的绝对路径（如 `/www/myproject/venv/bin/python manage.py runserver`），不用激活也不用改 PATH。

> � **延伸：为什么 Java 要永久设，Python 虚拟环境不用？**
>
> 核心区别：**Java 的运行时（JDK）是全局共用的，Python 的运行时（venv）是项目级隔离的。**
>
> | | Java | Python |
> |---|---|---|
> | 运行时 | 全局共用一个 JDK（一般服务器只装一个版本） | 每个项目有自己的 venv（独立的 python 和依赖） |
> | 依赖隔离 | Maven/Gradle 管理 jar 包版本，JDK 全局共用 | venv 隔离，每个项目可装不同版本的 Django/requests |
> | 环境变量 | `JAVA_HOME` 必须永久设（Tomcat/Maven 等启动脚本要读它，没设就启动失败） | 不用永久设，`source activate` 临时激活即可 |
>
> 一句话：**Java 程序启动时强依赖 `JAVA_HOME`，且 JDK 全局只有一个，所以永久设；Python 项目靠 venv 隔离，每个项目环境不同，所以临时激活。**

> � 两种写法对比：
> | 写法 | 位置 | 生效范围 | 推荐度 |
> |------|------|----------|--------|
> | `/etc/profile.d/xxx.sh` | 独立文件 | 所有用户 | ⭐ 推荐，干净好管理 |
> | `/etc/profile` 末尾 | 系统主文件 | 所有用户 | 不推荐，改错影响全局 |
> | `~/.bashrc` 末尾 | 用户主目录 | 仅当前用户 | 个人环境用 |

### 7.3.5 最常见的环境变量（开发只需要这几个）
> 🎯 **作用**：别去记几十个变量，开发日常只碰这 5 个。其他变量（LANG、LIBRARY_PATH 等）运维/编译时才会用到，开发遇到再说。

| 变量名 | 作用 | 例子 |
|--------|------|------|
| **PATH** | 命令查找路径 | `/usr/local/sbin:/usr/local/bin:...` |
| **JAVA_HOME** | JDK 安装目录 | `/usr/local/java/jdk8` |
| **VIRTUAL_ENV** | 当前 Python 虚拟环境路径 | `/root/env36` |
| **HOME** | 当前用户家目录 | `/root` |
| **PWD** | 当前所在目录 | `/opt/app` |
| **USER** | 当前用户名 | `root` |

> 💡 **CLASSPATH 不用配**：网上老教材喜欢写 `CLASSPATH=.:$JAVA_HOME/lib`，现代 JDK（1.5+）和工具链都不需要，配了反而可能出问题。**只配 JAVA_HOME + PATH 两行就够**。

### 7.3.6 常见坑
> 🎯 **作用**：配环境变量时最容易踩的 3 个坑，提前知道就不用花半天排查。

**坑 1：`$JAVA_HOME` 写成 `JAVA_HOME`**

```bash
export PATH=JAVA_HOME/bin:$PATH    # ❌ 错！系统会去找一个叫 JAVA_HOME 的目录
export PATH=$JAVA_HOME/bin:$PATH   # ✅ 对！$ 表示取变量的值
```

**坑 2：PATH 顺序错了，旧 JDK 还在用**

```bash
# 系统自带的 java 在 /usr/bin，你新装的在 /usr/local/java/jdk8/bin
export PATH=$PATH:$JAVA_HOME/bin   # ❌ 旧的在前面，还是用系统的 java
export PATH=$JAVA_HOME/bin:$PATH   # ✅ 新的放前面，覆盖系统的
which java                         # 验证用的是哪个
```

**坑 3：改完没 source 就以为没生效**

```bash
vim /etc/profile.d/java_env.sh     # 改完保存
# 直接敲 java -version 还是旧的？
source /etc/profile.d/java_env.sh  # 必须 source 才会重新加载
java -version                      # 现在才是新的
```

**坑 4（Python 专属）：装了包却 import 不到，因为装到别的 Python 里了**

```bash
# 系统装了 python3，又建了虚拟环境 venv
pip3 install requests              # ❌ 装到系统 python 里了
source venv/bin/activate
python3 -c "import requests"        # 报错 ModuleNotFoundError

# ✅ 正确做法：先激活虚拟环境再装包
source venv/bin/activate
pip install requests               # 装到当前虚拟环境
python3 -c "import requests"        # 成功

# 或者用 venv 的 pip 绝对路径
/www/myproject/venv/bin/pip install requests
```

> 💡 **要不要装 Anaconda？**
>
> **部署 Django/Flask 项目：不用装，用 venv 就够。** Anaconda 是给数据分析用的（带 numpy/pandas 等几百 MB 的包），服务器上部署 Web 项目不需要。
>
> | 场景 | 推荐 | 原因 |
> |------|------|------|
> | Django/Flask 部署 | `venv`（Python 自带） | 轻量、够用、pip 能装所有依赖 |
> | 数据科学/机器学习 | Anaconda/Miniconda | conda 能装 CUDA、MKL 等非 Python 依赖 |
> | 需要多 Python 版本共存（3.8 + 3.12） | Miniconda 或 pyenv | venv 只能基于已有的 Python 版本创建 |
>
> **一句话**：Web 开发用 venv，数据科学用 conda。

## 8. JDK 安装配置（必会）
> 🏷️ ⭐ 开发必会 —— 跑 Java 应用（Tomcat、Spring Boot）的前提

### 8.1 安装 JDK（必会）
> 🏷️ ⭐ 开发必会 —— 一条命令装完 OpenJDK，优先走这条路

**① 先说清楚：两种方式怎么选**

| 方式 | 一句话说明 | 适合谁 |
|------|-----------|--------|
| **方式一：YUM 装 OpenJDK（推荐）** | 一条命令装完，环境变量全自动 | 学习机、绝大多数场景 |
| **方式二：手动 tar.gz 装** | 版本自己挑，环境变量自己配 | 公司指定 Oracle JDK 或特定小版本时 |

> ⚠️ **前提**：CentOS base 源必须已修好（7.1 节）。好消息是 JDK 在 CentOS 7 的 **base 源**里（不走 EPEL），所以只需要 base 源通就行，EPEL 坏了不影响 JDK。

**② 方式一：YUM 安装（2 步）**

```bash
# 第 1 步：安装 OpenJDK 8（-devel 含 javac 编译器，必装；只装不带 devel 的运行不了源码）
sudo yum install -y java-1.8.0-openjdk java-1.8.0-openjdk-devel

# 第 2 步：验证（两条都能出版本号即成功）
java -version
# 输出类似：openjdk version "1.8.0_402"
javac -version
# 输出类似：javac 1.8.0_402
```

> 💡 YUM 方式**不用配 JAVA_HOME**：java/javac 已自动进 PATH。个别软件（比如手动装的 Tomcat）非要找 JDK 家目录时，用这条查真实路径：
> ```bash
> readlink -f $(which java)     # 输出类似 /usr/lib/jvm/java-1.8.0-openjdk-1.8.0.402.../jre/bin/java
> ```
> 去掉结尾的 `/jre/bin/java` 就是 JAVA_HOME。

### 8.2 手动安装 JDK（备选方式）（必会）
> 🏷️ ⭐ 开发必会 —— 公司指定 Oracle JDK / 特定版本时用，重点学环境变量写法

```bash
# 第 1 步：上传 jdk-8uXXX-linux-x64.tar.gz 到服务器（XFTP 或 scp 都行，见第一章 10.2 节）
# 第 2 步：解压到统一目录并简化名字
mkdir -p /usr/local/java
tar -xzf jdk-8u201-linux-x64.tar.gz -C /usr/local/java/
mv /usr/local/java/jdk1.8.0_201 /usr/local/java/jdk8

# 第 3 步：写环境变量（放 /etc/profile.d/ 下，所有用户自动加载，写法详见本章 7.3 节）
vi /etc/profile.d/java.sh
```

```bash
# /etc/profile.d/java.sh 内容
export JAVA_HOME=/usr/local/java/jdk8
export PATH=$JAVA_HOME/bin:$PATH
```

```bash
# 第 4 步：生效并验证
source /etc/profile.d/java.sh
java -version          # 出现 java version "1.8.0_201" 即成功
echo $JAVA_HOME        # 顺手确认变量已生效
```

> 💡 环境变量只写 JAVA_HOME 和 PATH 两行就够——网上的 CLASSPATH 三件套写法是老教材习惯，现在的工具链（javac/java/Tomcat）都不需要。

### 8.3 卸载 JDK（需要时用）

JDK 有两种安装方式，卸载方法不同，**对应用你当时的安装方式选一种**：

**方式一的卸载（YUM 装的 OpenJDK）：**

```bash
# 1. 卸载所有 java-1.8.0-openjdk 相关包
sudo yum remove -y java-1.8.0-openjdk java-1.8.0-openjdk-devel

# 2. 如果还有其他版本的 OpenJDK，也一起删（按你实际装的版本改）
sudo yum remove -y java-*-openjdk java-*-openjdk-devel

# 3. 清理可能的残留环境变量文件（如果之前手动写过）
sudo rm -f /etc/profile.d/java.sh

# 4. 验证
java -version                         # 应该: command not found
javac -version                        # 应该: command not found
which java                            # 应该: no java in (...)
rpm -qa | grep -i openjdk             # 应该没有输出
```

**方式二的卸载（手动 tar.gz 装的）：**

```bash
# 1. 先删掉环境变量文件（不然 source 后 JAVA_HOME 还指向已删的目录）
sudo rm -f /etc/profile.d/java.sh

# 2. 删掉 JDK 安装目录（按你实际解压的路径）
sudo rm -rf /usr/local/java/jdk8

# 3. 如果 /usr/local/java 目录空了，也可以一起删
sudo rm -rf /usr/local/java

# 4. 让当前终端的环境变量失效（重新登录也行）
unset JAVA_HOME
hash -r                                # 清除命令缓存，不然 which java 可能还指旧路径

# 5. 验证
java -version                         # 应该: command not found
echo $JAVA_HOME                        # 应该空
which java                            # 应该: no java in (...)
```

## 9. Tomcat 安装配置（必会）
> 🏷️ ⭐ 开发必会 —— Java Web 应用的运行容器，装完 JDK 就轮到它

### 9.1 下载安装（必会）
> 🏷️ ⭐ 开发必会 —— Tomcat 官方只发 tar.gz 包，解压即装（绿色软件）

Tomcat 没有 yum 源可用，**手动解压就是标准装法**（这点和 MySQL/JDK 不同）：

```bash
# 第 1 步：下载（版本号去 tomcat.apache.org 挑，这里以当前稳定版 9.0.120 为例）
# 说明：Tomcat 9.0 是长期支持版本（LTS），要求 Java 8+，与 OpenJDK 8 完全兼容；
#       Tomcat 8.5 已于 2024-03-31 停止维护（EOL），官方已下架，新装机直接用 9.0
# ⚠️ 下载源优先级：dlcdn.apache.org（官方 CDN） → archive.apache.org（官方归档备份）
#   国内服务器如果 dlcdn 太慢/超时，换 archive 源（archive 是官方永久归档，版本更全）
cd /usr/local/src                                  # 安装包统一放这，好管理
sudo yum install -y wget                           # 最小化安装的 CentOS 7 默认没 wget，先装上（已装可跳过）

# 方式 A：官方 CDN 下载（推荐，实时同步最新版）
sudo wget https://dlcdn.apache.org/tomcat/tomcat-9/v9.0.120/bin/apache-tomcat-9.0.120.tar.gz

# 方式 B：官方归档下载（dlcdn 超时就换这个，归档里也有 9.0.121/9.0.122 等新版）
# sudo wget https://archive.apache.org/dist/tomcat/tomcat-9/v9.0.120/bin/apache-tomcat-9.0.120.tar.gz

# 第 2 步：解压到 /usr/local 并简化目录名
sudo tar -xzf apache-tomcat-9.0.120.tar.gz -C /usr/local/
sudo mv /usr/local/apache-tomcat-9.0.120 /usr/local/tomcat

# 第 3 步：验证——启动脚本存在即装完
ls /usr/local/tomcat/bin/startup.sh
```

> 💡 不用配 CATALINA_HOME 环境变量：脚本会自动推算自己的位置，直接用全路径调用即可。

### 9.2 启动与管理（必会）
> 🏷️ ⭐ 开发必会 —— 启动、看日志、放行防火墙、浏览器验证，一条龙

```bash
# 第 1 步：启动
/usr/local/tomcat/bin/startup.sh
# 输出最后一行：Tomcat started.    ← 看到这句才是启动成功

# 第 2 步：看日志确认没报错（Ctrl+C 只是退出查看，不影响 Tomcat 运行）
tail -f /usr/local/tomcat/logs/catalina.out

# 第 3 步：防火墙放行 8080（不放行浏览器打不开，防火墙详见 5.4）
firewall-cmd --add-port=8080/tcp --permanent
firewall-cmd --reload

# 第 4 步：Windows 浏览器访问 http://虚拟机IP:8080，看到 Tomcat 欢迎页即全部成功
```

```bash
# 日常管理三件套
/usr/local/tomcat/bin/shutdown.sh              # 停止
ss -tlnp | grep 8080                           # 确认端口在听（有输出=在跑）
tail -100f /usr/local/tomcat/logs/catalina.out # 开发期最常敲：盯日志
```

**两个高频坑：**

```bash
# 坑1：启动报 "Neither the JAVA_HOME nor the JRE_HOME environment variable is defined"
# 原因：Tomcat 找不到 JDK（yum 装的 java 不会自动设置 JAVA_HOME）
# 解决：建 setenv.sh（Tomcat 启动时会自动加载它），JAVA_HOME 用 8.1 节的 readlink 方法求出
echo "JAVA_HOME=$(readlink -f $(which java) | sed 's|/jre/bin/java||')" > /usr/local/tomcat/bin/setenv.sh

# 坑2：startup.sh 显示 started 但浏览器打不开
# 排查顺序：ss -tlnp | grep 8080 在不在听 → 防火墙放行没 → IP 填对没
```

### 9.3 创建 Systemd 服务（必会）
> 🏷️ ⭐ 开发必会 —— 让 Tomcat 像 nginx 一样 systemctl 管理 + 开机自启

手动解压装的 Tomcat 默认不会开机自启，写一个服务文件交给 systemd 管（命令写法见 5.1 节）：

```bash
vi /etc/systemd/system/tomcat.service
```

```ini
[Unit]
Description=Apache Tomcat 9
After=network.target

[Service]
Type=forking
# JAVA_HOME 按自己机器的实际路径填（readlink -f $(which java) 查）
Environment=JAVA_HOME=/usr/lib/jvm/java-1.8.0-openjdk
ExecStart=/usr/local/tomcat/bin/startup.sh
ExecStop=/usr/local/tomcat/bin/shutdown.sh
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload      # 让 systemd 认识新服务文件
systemctl enable --now tomcat   # 启动 + 开机自启
systemctl status tomcat         # active (running) 即成功
```

### 9.4 部署应用与常用配置（必会）
> 🏷️ ⭐ 开发必会 —— 把自己的 war 包跑起来，这才是装 Tomcat 的目的

**① 部署应用（最常用，就一步）**

```bash
# 把 war 包丢进 webapps，Tomcat 会自动解压部署
cp myapp.war /usr/local/tomcat/webapps/

# 访问 http://虚拟机IP:8080/myapp（路径 = war 包文件名）
ls /usr/local/tomcat/webapps/        # 能看到同名目录说明解压完成
```

**② 改端口（可选，8080 冲突时）**

```bash
vim /usr/local/tomcat/conf/server.xml    # 找到 port="8080" 改成别的（如 8888）
grep 'port="8080"' /usr/local/tomcat/conf/server.xml   # 定位那行
/usr/local/tomcat/bin/shutdown.sh && /usr/local/tomcat/bin/startup.sh   # 改完重启
```

**③ webapps 里的自带目录（了解）**

`docs`、`examples` 是官方自带示例应用，学习完可以删掉（`rm -rf /usr/local/tomcat/webapps/{docs,examples}`），减少暴露面。

> 💡 虚拟主机、多实例等 server.xml 高级配置属于运维向，开发用到时再查官方文档，本课件不展开。

### 9.5 卸载 Tomcat（需要时用）

Tomcat 是解压安装的，卸载就是删目录 + 清理服务文件。

```bash
# 1. 停止服务（两种方式二选一，看你当时怎么启动的）
# 如果是 systemd 管理的：
sudo systemctl stop tomcat
sudo systemctl disable tomcat

# 如果是手动 startup.sh 启动的：
# /usr/local/tomcat/bin/shutdown.sh

# 2. 删除 systemd 服务文件（如果创建过）
sudo rm -f /etc/systemd/system/tomcat.service
sudo systemctl daemon-reload

# 3. 删除 Tomcat 安装目录（按你实际解压的路径）
sudo rm -rf /usr/local/tomcat

# 4. 清理可能残留的日志（如果日志重定向到别处了）
sudo rm -rf /usr/local/src/apache-tomcat-*.tar.gz   # 删掉下载的安装包

# 5. 验证是否删干净
ls /usr/local/tomcat                    # 应该: No such file or directory
which tomcat                            # 应该: no tomcat in (...)
sudo ss -tlnp | grep :8080              # 8080 端口应该没人占用
systemctl status tomcat                 # 应该: Unit tomcat.service could not be found
```

## 10. MySQL 安装配置（必会）
> 🏷️ ⭐ 开发必会 —— 软件开发日常高频使用，务必掌握

### 10.1 版本选择与安装方式（必会）
> 🏷️ ⭐ 开发必会 —— 先定版本再动手，别装完才发现装错了

> ⚠️ **动手前的硬前提（CentOS 7.6 用户必读）**：必须先按 **7.1.0 节**修好 yum 源，再来装 MySQL。
> 原因：MySQL 仓库本身（dev.mysql.com）没问题，但 `mysql-community-server` 依赖的 `perl`、`libaio`、`net-tools` 等基础包来自 CentOS base 源。base 源失效时，`yum install mysql-community-server` 会报 `Could not retrieve mirrorlist ... mirrorlist.centos.org`。先把 base 源换成阿里云 vault（7.1.0），MySQL 才能装得上。

**① MySQL 5.7 还是 8.0？一张表说清楚**

| 对比项 | MySQL 5.7 | MySQL 8.0 |
|--------|-----------|-----------|
| 官方状态 | 2023-10 已停止维护（EOL），不再有安全更新 | 当前主流版本，持续更新维护 |
| 默认字符集 | `latin1`，存中文**必须手动改** utf8mb4 | 默认就是 `utf8mb4`，开箱即用 |
| 默认密码加密方式 | `mysql_native_password`，老版 Navicat 直连没问题 | `caching_sha2_password`（更安全），太老的图形化工具会连不上 |
| 密码策略变量名 | `validate_password_policy`（下划线） | `validate_password.policy`（中间是**点**） |
| 性能 / 新语法 | 够用，老项目存量大 | 性能更好，支持窗口函数、CTE 等新特性 |
| 适合场景 | 公司老系统维护、教程/教材仍是 5.7 | ⭐ 新项目、求职面试（主流要求 8.0） |

> 💡 **怎么选？** 学习、新项目直接装 **8.0**；只有接手的公司老项目线上就是 5.7 时，为保持环境一致才装 5.7。两者基础 SQL 完全一样，会一个再上手另一个零成本。
>
> ⚠️ **一台机器只装一个版本，二选一**。5.7 和 8.0 的服务名都叫 `mysqld`、数据目录都是 `/var/lib/mysql`，混装必然冲突。下面 10.2、10.3 只跟着你选的那条线走，**不要两条都执行**；装完之后的配置（10.4 起）两个版本通用。

**② 3 种安装方式怎么选**

| 方式 | 一句话说明 | 适合谁 |
|------|-----------|--------|
| ① MySQL 官方 YUM 源（推荐） | 几条命令装完，服务、配置、开机自启全自动 | 学习机、绝大多数场景 |
| ② MariaDB | CentOS 自带源里的"MySQL 平替"，命令几乎一样 | 只想练 SQL、不在乎是 MySQL 还是 MariaDB |
| ③ 手动二进制安装 | 下载 tar 包自己解压、初始化、写服务 | 运维向，开发用不上，本课件不讲 |

> 下面 10.2 / 10.3 都按推荐的**方式一**走完整流程（已按 10.1 节开头提示修好源）。

### 10.2 MySQL 5.7 安装与首次登录（必会）
> 🏷️ ⭐ 开发必会 —— 选 5.7 的跟本节走；选 8.0 的直接跳到 10.3

**① 安装（4 步）**

```bash
# 第 1 步：安装 MySQL 5.7 官方 yum 源（本质是往 /etc/yum.repos.d/ 放一个仓库配置文件）
sudo rpm -Uvh https://dev.mysql.com/get/mysql57-community-release-el7-11.noarch.rpm

# 第 2 步：导入 2022 年后的新 GPG 密钥（不导入下一步会报 "GPG key ... is not installed"）
sudo rpm --import https://repo.mysql.com/RPM-GPG-KEY-mysql-2022

# 第 3 步：安装服务端（会自动带上客户端 mysql 命令）
sudo yum install -y mysql-community-server

# 第 4 步：确认装好了（能看到 5.7 版本号即成功）
mysql --version
# 输出类似：mysql  Ver 14.14 Distrib 5.7.44
```

**② 启动并拿到临时密码（首次登录 5 步）**

YUM 方式安装时初始化是自动完成的（这和手动安装要自己跑 `mysqld --initialize` 不同），首次启动后直接走下面 5 步：

```bash
# 第 1 步：启动并设置开机自启
systemctl enable --now mysqld
systemctl status mysqld                 # 看到 active (running) 即成功

# 第 2 步：从日志里找 root 的临时密码（5.7 首次启动自动生成，拿不到它进不去）
grep 'temporary password' /var/log/mysqld.log
# 输出类似：A temporary password is generated for root@localhost: rq!fK2j9$pLm

# 第 3 步：用临时密码登录（输入时屏幕不显示是正常的）
mysql -u root -p

# 第 4 步：登录进去第一件事——改掉临时密码
mysql> ALTER USER 'root'@'localhost' IDENTIFIED BY 'Root@123456';
Query OK, 0 rows affected                # 出现 OK 就是改成功了

# 第 5 步：退出后用新密码重登一次，验证生效
mysql> quit
mysql -u root -p                         # 输入新密码 Root@123456
```

> ⚠️ **报 ERROR 1819（密码不满足策略）？** 5.7 默认密码策略要求：8 位以上 + 含大小写 + 数字 + 特殊符号。学习机想设简单密码（如 `root1234`），登录后执行（注意 5.7 变量名是**下划线**）：
> ```sql
> SHOW VARIABLES LIKE 'validate_password%';   -- 先看当前策略
> SET GLOBAL validate_password_policy = LOW;  -- 只要求长度
> SET GLOBAL validate_password_length = 6;    -- 最短 6 位
> ```
> 注意：这样改重启 MySQL 后失效；想永久生效就写进 /etc/my.cnf（见 10.4）。

**③ 备选：装 MariaDB 代替（3 条命令，更省事）**

```bash
sudo yum install -y mariadb-server mariadb
systemctl enable --now mariadb          # 启动 + 开机自启
mysql_secure_installation               # 交互式安全初始化：设 root 密码、删匿名用户等，按提示答 y
```

> 💡 MariaDB 是 MySQL 的社区开源分支，`mysql` 客户端命令、SQL 语法基本通用，练 SQL 完全够用。走这条线的话，后面小节里的 `mysqld` 换成 `mariadb` 即可。

### 10.3 MySQL 8.0 安装与首次登录（必会）
> 🏷️ ⭐ 开发必会 —— ⭐ 学习和新项目推荐走这条线；已装 5.7 的跳过本节

**① 安装（4 步）——和 5.7 几乎一样，只有第 1 步包名不同**

```bash
# 第 1 步：安装 MySQL 8.0 官方 yum 源（包名里是 mysql80，装完默认启用 8.0 子仓库）
sudo rpm -Uvh https://dev.mysql.com/get/mysql80-community-release-el7-11.noarch.rpm

# 第 2 步：导入新 GPG 密钥（和 5.7 用的是同一把 2022 新密钥）
sudo rpm --import https://repo.mysql.com/RPM-GPG-KEY-mysql-2022

# 第 3 步：安装服务端（会自动带上客户端 mysql 命令）
sudo yum install -y mysql-community-server

# 第 4 步：确认装好了（能看到 8.0 版本号即成功）
mysql --version
# 输出类似：mysql  Ver 8.0.42 for Linux on x86_64 (MySQL Community Server - GPL)
```

> 💡 想确认装的确实是 8.0：执行 `yum repolist enabled | grep mysql`，看到 `mysql80-community` 就对了。

**② 启动并拿到临时密码（首次登录 5 步，流程和 5.7 完全一样）**

```bash
# 第 1 步：启动并设置开机自启
systemctl enable --now mysqld
systemctl status mysqld                 # 看到 active (running) 即成功

# 第 2 步：从日志里找 root 的临时密码（8.0 同样是首次启动自动生成）
grep 'temporary password' /var/log/mysqld.log
# 输出类似：A temporary password is generated for root@localhost: rq!fK2j9$pLm

# 第 3 步：用临时密码登录（输入时屏幕不显示是正常的）
mysql -u root -p

# 第 4 步：登录进去第一件事——改掉临时密码
mysql> ALTER USER 'root'@'localhost' IDENTIFIED BY 'Root@123456';
Query OK, 0 rows affected                # 出现 OK 就是改成功了

# 第 5 步：退出后用新密码重登一次，验证生效
mysql> quit
mysql -u root -p                         # 输入新密码 Root@123456
```

> ⚠️ **报 ERROR 1819？** 8.0 默认密码策略同样要求：8 位以上 + 含大小写 + 数字 + 特殊符号。学习机想设简单密码，登录后执行（**变量名中间是点，和 5.7 的下划线写法不一样**）：
> ```sql
> SHOW VARIABLES LIKE 'validate_password.%';  -- 8.0 用点号前缀查
> SET GLOBAL validate_password.policy = LOW;  -- 只要求长度
> SET GLOBAL validate_password.length = 6;    -- 最短 6 位
> ```
> 8.0 的密码校验由"组件（component）"内置提供（5.7 是插件），所以变量名统一带 `validate_password.` 前缀。重启后失效；想永久生效写进 /etc/my.cnf（见 10.4）。

> 💡 **8.0 装好后和 5.7 的两个自带差异，先有个印象，后面会逐个处理：**
> - **字符集**：8.0 默认已经是 `utf8mb4`，中文直接能存（5.7 必须手动改，见 10.4）；
> - **密码加密方式**：8.0 默认 `caching_sha2_password`，老版本 Navicat 远程连接会报错，10.5 有专门的处理办法。

#### 卸载 MySQL（需要时用）

> ⚠️ **卸载前先停服务，且数据会全丢！** 有重要数据先 `mysqldump` 备份。

```bash
# 1. 停止服务 + 取消开机自启
sudo systemctl stop mysqld
sudo systemctl disable mysqld

# 2. 卸载所有 MySQL 相关包（用通配符一次卸干净）
sudo yum remove -y mysql-community-*

# 3. 清理残留（数据、配置、日志，yum remove 不会删这些）
sudo rm -rf /var/lib/mysql              # 数据库文件（⚠️ 数据全丢！）
sudo rm -rf /var/log/mysqld.log          # 日志文件
sudo rm -rf /etc/my.cnf                  # 主配置文件
sudo rm -rf /etc/my.cnf.d               # 配置目录
sudo rm -rf /var/run/mysqld              # 运行时 pid/socket 文件

# 4. 如果装了 MySQL 仓库，也可以一起删（不影响其他软件）
sudo yum remove -y mysql80-community-release   # 8.0 装的仓库
# 或者 5.7：sudo yum remove -y mysql57-community-release

# 5. 验证是否删干净
which mysql                            # 应该: no mysql in (...)
rpm -qa | grep mysql                   # 应该没有输出
sudo ss -tlnp | grep :3306             # 3306 端口应该没人占用
```

### 10.4 配置文件与字符集（必会）
> 🏷️ ⭐ 开发必会 —— 5.7 不改字符集，中文存进去变 "???"；8.0 用户可快速扫过

YUM 方式装完，配置文件是现成的 `/etc/my.cnf`（不用自己新建），默认路径：数据目录 `/var/lib/mysql`、日志 `/var/log/mysqld.log`。

**最需要关心的一件事：字符集。**

- **5.7：必做。** 默认 `latin1`，不改成 `utf8mb4`，中文会变问号或乱码；
- **8.0：默认已配好。** 默认就是 `utf8mb4`，本节可以跳过；想统一配置习惯照着做一遍也没有副作用。

```bash
cp /etc/my.cnf /etc/my.cnf.bak          # 改前先备份（配置写错 MySQL 会起不来）
vim /etc/my.cnf
```

```ini
[mysqld]
character-set-server=utf8mb4            # 服务端字符集（5.7 存中文必配；8.0 默认已是它）
collation-server=utf8mb4_unicode_ci     # 排序规则（8.0 默认是 utf8mb4_0900_ai_ci，照写也兼容）
# 学习机想放开密码策略（对应 10.2 / 10.3 的 ERROR 1819），按自己的版本只加对应两行：
# —— 5.7 写法（下划线）：
# validate_password_policy=LOW
# validate_password_length=6
# —— 8.0 写法（点号，别写错）：
# validate_password.policy=LOW
# validate_password.length=6

[client]
default-character-set=utf8mb4           # 客户端字符集

[mysql]
default-character-set=utf8mb4           # 命令行登录字符集
```

```bash
systemctl restart mysqld                # 重启生效

# 进 mysql 验证：character_set_server / character_set_database 都是 utf8mb4 即成功
mysql -u root -p -e "SHOW VARIABLES LIKE 'character%';"
```

> 💡 原配置里的端口（3306）、日志路径等保持默认就好。配置改错导致起不来时，先恢复备份 `cp /etc/my.cnf.bak /etc/my.cnf`，再看 `/var/log/mysqld.log` 找报错原因。

### 10.5 远程访问与防火墙（必会）
> 🏷️ ⭐ 开发必会 —— 用 Windows 的 Navicat / DataGrip 连虚拟机里的 MySQL，必配（5.7 / 8.0 通用）

MySQL 默认只允许本机登录（root@localhost），从 Windows 图形化工具直连会被拒。两步打通：

```bash
# 第 1 步：建一个专用于远程登录的账号（别开 root@%，风险太大）
mysql -u root -p
mysql> CREATE USER 'dev'@'%' IDENTIFIED BY 'Dev@123456';   # % = 不限制来源 IP
mysql> GRANT ALL PRIVILEGES ON *.* TO 'dev'@'%';           # 授全部库全部权限（学习机图省事）
mysql> FLUSH PRIVILEGES;                                   # 刷新权限立即生效
mysql> quit
```

```bash
# 第 2 步：防火墙放行 3306 端口（不放行外部照样连不上，防火墙详见 5.4）
firewall-cmd --add-port=3306/tcp --permanent
firewall-cmd --reload

# 查虚拟机 IP（Windows 工具里"主机"就填这个）
ip addr | grep inet
```

在 Windows 的 Navicat / DataGrip 里填：主机 = 虚拟机 IP（如 `192.168.100.100`）、端口 `3306`、用户 `dev`、密码 `Dev@123456`，测试连接即可。

> ⚠️ **8.0 专属坑：报 `Authentication plugin 'caching_sha2_password' cannot be loaded`？**
> 8.0 默认改用新加密插件，老版本 Navicat（12.1 以前）不认识它。两个办法选一个：
> - **办法一（推荐）**：把 Navicat / DataGrip 升级到新版本，新版原生支持这种加密；
> - **办法二**：把远程账号改成老的加密方式（学习机够用），登录 mysql 后执行：
> ```sql
> ALTER USER 'dev'@'%' IDENTIFIED WITH mysql_native_password BY 'Dev@123456';
> FLUSH PRIVILEGES;
> ```
> 5.7 默认本来就是 `mysql_native_password`，不会遇到这个问题。

> 💡 还是连不上？按三件事排查：MySQL 起了没（`systemctl status mysqld`）→ 端口放了没（`firewall-cmd --list-ports`）→ IP 通不通（Windows 里 `ping 虚拟机IP`）。

### 10.6 MySQL 常用操作（必会）
> 🏷️ ⭐ 开发必会 —— 用户与权限管理 SQL，5.7 / 8.0 通用

```sql
-- 查看用户
SELECT user, host FROM mysql.user;

-- 创建用户
CREATE USER 'appuser'@'localhost' IDENTIFIED BY 'password';

-- 授权
GRANT SELECT, INSERT, UPDATE, DELETE ON mydb.* TO 'appuser'@'localhost';
GRANT ALL PRIVILEGES ON mydb.* TO 'appuser'@'localhost';
FLUSH PRIVILEGES;

-- 刷新权限
FLUSH PRIVILEGES;

-- 查看权限
SHOW GRANTS FOR 'appuser'@'localhost';

-- 删除用户
DROP USER 'appuser'@'localhost';

-- 修改密码
ALTER USER 'appuser'@'localhost' IDENTIFIED BY 'new_password';
```

> ⚠️ **8.0 注意**：不能再用 `GRANT ALL ON *.* TO '用户'@'%' IDENTIFIED BY '密码';` 一句话同时建账号+授权了，必须像上面这样**先 `CREATE USER` 再 `GRANT`**。这套写法 5.7 同样支持，照这一种写法两个版本都不会错。

### 10.7 找回 MySQL root 密码（必会）
> 🏷️ ⭐ 开发必会 —— 忘了 root 密码的救命流程，两个版本做法不同，按自己装的版本对号入座

**① MySQL 5.7：mysqld_safe 跳过权限验证（5 步）**

```bash
# 1. 停止 MySQL
systemctl stop mysqld

# 2. 跳过权限验证启动
mysqld_safe --skip-grant-tables &

# 3. 免密登录
mysql -u root

# 4. 修改密码（skip-grant 模式下必须先 FLUSH PRIVILEGES，ALTER USER 才执行得了）
FLUSH PRIVILEGES;
ALTER USER 'root'@'localhost' IDENTIFIED BY 'new_password';
FLUSH PRIVILEGES;

# 5. 关闭免密实例，再正常启动
mysqladmin -u root -p shutdown
systemctl start mysqld
```

**② MySQL 8.0：my.cnf 临时加 skip-grant-tables（5 步，推荐）**

> 8.0 在 RPM + systemd 环境下，最稳的办法是往配置文件临时加一行 `skip-grant-tables`，比直接敲 mysqld_safe 少踩环境坑。

```bash
# 1. 停止 MySQL
systemctl stop mysqld

# 2. 编辑 /etc/my.cnf，在 [mysqld] 段落下临时加一行：skip-grant-tables

# 3. 重启后免密登录
systemctl start mysqld
mysql -u root

# 4. 先 FLUSH PRIVILEGES 让权限表生效，再改密码
FLUSH PRIVILEGES;
ALTER USER 'root'@'localhost' IDENTIFIED BY 'Root@123456';
FLUSH PRIVILEGES;

# 5. 删掉 my.cnf 里刚加的 skip-grant-tables 那行，再正常重启（必须做！）
systemctl restart mysqld
```

> ⚠️ `skip-grant-tables` 期间等于数据库完全不验身份、谁都能进，**操作完务必删掉这行并重启**，千万别留在配置里。

## 11. Nginx 安装配置（必会）
> 🏷️ ⭐ 开发必会 —— Nginx 是部署时最常用的 Web 服务器 / 反向代理，前面 5.1、5.4 一直拿它举例，这一节真正把它装上、跑通、学会改一个最简单的网站

### 11.1 Nginx 是干嘛的（先知道为什么装）

Nginx（读作"engine-x"）是一个**高性能 Web 服务器**，开发 / 部署时主要用它做三件事：

| 用途 | 说明 | 类比 |
|------|------|------|
| **提供静态网站** | 把 HTML/CSS/JS、图片、Vue 打包后的 dist 直接发给浏览器 | 餐厅的**展示柜**，直接取现成的菜 |
| **反向代理** | 浏览器请求先到 Nginx，再由它转发给后端 Django/Tomcat（如 `/api/` 转给 8000 端口） | 餐厅的**前台**，把客人领到对应窗口 |
| **负载均衡 / HTTPS** | 多台后端分流、配置证书（生产进阶，本节不展开） | — |

> 本节只做"**装上 → 跑起来 → 浏览器看到欢迎页 → 改成自己的页面**"这一条主线。反向代理的具体写法在后面项目部署章节讲。

### 11.2 安装方式怎么选（先选对方法，别乱装）

CentOS 7 上装 Nginx 常见有 3 种方式，**本课件主线用方法一（YUM + EPEL）**：

| 方式 | 装到的版本 | 优点 | 缺点 | 推荐度 |
|------|-----------|------|------|--------|
| **方法一：YUM + EPEL 源** | 1.20.1 | 一条命令、自动配好 systemd、好卸载、国内镜像快 | 版本不是最新 | ⭐⭐⭐⭐⭐ 学习/生产首选 |
| **方法二：Nginx 官方源** | 1.24+ 较新 | 版本新、官方维护 | 要手动配 repo、国内访问可能慢 | ⭐⭐ 想要新版时 |
| ③ 源码编译安装 | 任意版本 | 可定制模块/路径 | 步骤繁琐、要装编译器、不便升级 | ⭐ 新手不推荐 |

> ⚠️ **关键前提**：Nginx **不在 CentOS 7 官方 base 源里**。方法一走 EPEL 扩展源，方法二走 Nginx 官方自己的源。**两套源不要同时启用**（yum 会从两个源都找到 nginx 包，版本冲突）。

### 11.3 方法一：YUM + EPEL 源（推荐，本课件主线）

#### 第 0 步：确认 CentOS base 源已修好

本章 7.1.0 节讲过 CentOS 7 源已失效。如果 `yum install` 还报 `Could not resolve host: mirrorlist.centos.org`，**先回去把 7.1.0 的换源做完**，否则下面全跑不动。能正常 `yum repolist` 看到 base/updates/extras 再继续。

#### 第 1 步：装 EPEL 扩展源（因为 nginx 在里面）

```bash
# 先写好 epel.repo 指向阿里云 epel-archive（先于装包，避免坏 epel.repo 让 yum 整体报错）
# ⚠️ 必须用 sudo tee，不能用 sudo cat >（sudo 不作用于重定向 >，会报"权限不够"）
sudo tee /etc/yum.repos.d/epel.repo > /dev/null << 'EOF'
[epel]
name=EPEL 7 - $basearch
baseurl=https://mirrors.aliyun.com/epel-archive/7/$basearch/
enabled=1
gpgcheck=0
EOF

# clean all = 清本地旧缓存；makecache = 重新联网拉新索引
# 换了 repo 文件后必须执行，否则 yum 可能还拿旧缓存报错
sudo yum clean all && sudo yum makecache

# 再确认/补装 epel-release（已装会提示 already installed）
rpm -q epel-release || sudo yum install -y epel-release
sudo yum repolist          # 能看到 epel 一行 = 成功
```

> 如果你之前装 htop / redis 时已经按 7.1 做过这一步，**整步跳过即可**。完整说明和 `gpgcheck` 规范化见 7.1 节。

#### 第 2 步：安装 Nginx

```bash
sudo yum install -y nginx
```

看到 `Complete!` 即安装成功。验证版本和是否装好：

```bash
nginx -v                  # 打印版本，如 nginx version: nginx/1.20.1
rpm -qa | grep nginx      # 能查到 nginx-1.20.x 包 = 确实装上了
which nginx               # /usr/sbin/nginx（可执行文件位置）
```

#### 第 3 步：启动 + 设置开机自启（一条命令）

```bash
sudo systemctl enable --now nginx
```

> `enable --now` = 立刻启动 + 开机自动启动（5.1 节讲的两个开关一次搞定）。

#### 第 4 步：处理防火墙（让外部能访问 80 端口）

二选一（详见 5.4 节）：

```bash
# 方式 A：学习机直接关防火墙（本课件实验推荐，最省事）
sudo systemctl stop firewalld && sudo systemctl disable firewalld

# 方式 B：保留防火墙，只放行 80 端口（更规范）
sudo firewall-cmd --permanent --add-port=80/tcp
sudo firewall-cmd --reload
```

#### 第 5 步：验证（本机 + Windows 浏览器两处都测）

```bash
# ① 看服务状态：Active: active (running) 即正常
systemctl status nginx

# ② 服务器本机访问，返回一大段 HTML（欢迎页源码）就成功
curl http://localhost
```

然后在 **Windows 浏览器**地址栏输入**虚拟机的 IP**（不是 localhost，localhost 在 Windows 上指你自己的电脑）：

```
http://192.168.x.x          # 换成你虚拟机的 IP（ip addr 查，见网络章节）
```

看到 **"Welcome to nginx!"** 页面 = 全链路打通：Nginx 在跑、端口通、防火墙放行了。

#### 第 6 步：卸载 Nginx（需要时用）

> ⚠️ **卸载前先停服务**：服务还在跑就删文件，可能删不干净（端口还占着、进程还在）。

```bash
# 1. 停止服务 + 取消开机自启
sudo systemctl stop nginx              # stop：立刻停止
sudo systemctl disable nginx           # disable：取消开机自启

# 2. 卸载软件包（yum 自动卸依赖）
sudo yum remove -y nginx

# 3. 清理残留（配置文件、日志、缓存目录，yum remove 不会自动删）
sudo rm -rf /etc/nginx                 # 配置文件目录
sudo rm -rf /var/log/nginx             # 日志目录
sudo rm -rf /var/cache/nginx           # 缓存目录
sudo rm -rf /usr/share/nginx           # 默认网页目录（欢迎页等）

# 4. 验证是否删干净（下面命令都查不到东西 = 删干净了）
which nginx                            # 应该输出: /usr/bin/which: no nginx in (...)
rpm -qa | grep nginx                   # 应该没有输出
sudo ss -tlnp | grep :80               # 80 端口应该没人占用
```

### 11.3-B 方法二：Nginx 官方源（想要新版时用）

> 方法一装的是 1.20.1，如果想要 1.24+ 新版，走这条路。**但注意：EPEL 源和官方源不要同时启用**，如果之前做过方法一又想切官方源，先删掉 EPEL 装的 nginx：`sudo yum remove -y nginx`。

#### 第 1 步：写 Nginx 官方 repo 文件

```bash
# 同样用 sudo tee 避免重定向权限问题
sudo tee /etc/yum.repos.d/nginx.repo > /dev/null << 'EOF'
[nginx-stable]
name=nginx stable repo
baseurl=http://nginx.org/packages/centos/$releasever/$basearch/
gpgcheck=0
enabled=1
EOF

# 清旧缓存、拉新索引
sudo yum clean all && sudo yum makecache
```

> 官方源里有两条：`nginx-stable`（稳定版，`enabled=1` 默认启用）和 `nginx-mainline`（主线开发版，默认 `enabled=0`）。平时用 stable 就行。

#### 第 2 步：安装 + 启动

和方法一完全一样：

```bash
sudo yum install -y nginx        # 装完 nginx -v 应该显示 1.24+
sudo systemctl enable --now nginx
```

#### 第 3 步：验证

```bash
nginx -v                         # 确认版本是 1.24+
systemctl status nginx           # Active: active (running)
curl http://localhost            # 返回欢迎页 HTML
```

> ⚠️ 官方源走 `http://nginx.org`，国内服务器可能下载慢。如果 `sudo yum install -y nginx` 卡很久或超时，换回方法一（EPEL 走阿里云镜像秒开）。

### 11.4 认识关键路径（yum 安装版，务必记住）

yum 装的 Nginx 文件分散在系统标准目录，**这几个路径开发天天碰**：

| 用途 | 路径 | 说明 |
|------|------|------|
| **主配置文件** | `/etc/nginx/nginx.conf` | 全局配置，**一般不改它** |
| **⭐ 自己的站点配置** | `/etc/nginx/conf.d/` | 写网站 / 反代配置放这个目录，文件名 `xxx.conf` |
| **⭐ 网站根目录** | `/usr/share/nginx/html/` | 放网页文件的地方，默认 `index.html` 就是欢迎页 |
| 访问日志 | `/var/log/nginx/access.log` | 记录每个请求（谁、访问了什么、状态码） |
| 错误日志 | `/var/log/nginx/error.log` | **启动失败/报错先看它** |
| 可执行程序 | `/usr/sbin/nginx` | nginx 命令本体 |

> 📌 **路径铁律（容易踩坑）**：yum 安装的 Nginx，自己加配置一律写到 **`/etc/nginx/conf.d/`** 目录（yum 装完这里自带一个 `default.conf`，默认站点就定义在里面），不要在主文件 `nginx.conf` 里乱加 server。
> （如果用的是宝塔面板，路径完全不同，在"网站→设置→配置文件"，实际位于 `/www/server/panel/vhost/nginx/`。）

### 11.5 改配置的正确流程（必会，三步不能乱）

改 Nginx 配置有固定套路，**每次都按这三步**，别直接改完就以为生效了：

```bash
# ① 改配置（用 vi 在 conf.d 目录里改，下面有最小示例）
sudo vi /etc/nginx/conf.d/default.conf

# ② 测试配置语法（-t = test）。必须显示 syntax is ok / test is successful 才能继续
sudo nginx -t

# ③ 平滑重载，让新配置生效（不断开正在访问的连接，比重启好）
sudo systemctl reload nginx
```

> ⚠️ **先 `-t` 再 `reload`**：如果配置有语法错误却直接 reload，Nginx 会拒绝加载、继续跑旧配置；更糟的情况是 restart 会直接起不来。养成"改完必 `nginx -t`"的习惯。

#### 动手：把欢迎页换成自己的页面

**① 建一个自己的网页文件**：

```bash
# 在网站根目录建 test.html
sudo vi /usr/share/nginx/html/test.html
```

写入内容（`:wq` 保存）：

```html
<h1>我的第一个 Nginx 页面</h1>
<p>Hello from Nginx on CentOS 7!</p>
```

**② 浏览器访问** `http://虚拟机IP/test.html`，看到你写的标题就成功了——不用改任何配置，因为默认站点的根目录本来就指向 `/usr/share/nginx/html/`。

#### 最小 server 配置长什么样（读懂即可）

打开 `/etc/nginx/conf.d/default.conf`，yum 装完默认大致是这样（逐行注释）：

```nginx
server {
    listen       80;                  # 监听 80 端口（HTTP 默认端口）
    server_name  localhost;           # 域名/IP，学习阶段用 localhost 或 _ 匹配所有

    location / {                      # 当访问路径是 /（根路径）时
        root   /usr/share/nginx/html; # 去这个目录找文件
        index  index.html index.htm;  # 默认依次找 index.html → index.htm 返回
    }

    error_page  500 502 503 504  /50x.html;   # 出错时跳转的页面
}
```

读懂这 5 行（`listen / server_name / location / root / index`）就够开发日常用了。比如想让网站跑在 **8080 端口**，把 `listen 80;` 改成 `listen 8080;`，`nginx -t` + `reload`，再放行/关闭对应端口防火墙即可。

### 11.6 常用命令速查

```bash
# 服务控制（systemctl，5.1 节同一套）
sudo systemctl start nginx      # 启动
sudo systemctl stop nginx       # 停止
sudo systemctl restart nginx    # 重启（配置坏了/要完全重来时）
sudo systemctl reload nginx     # ⭐ 改完配置平滑重载（日常用这个）
systemctl status nginx          # 看状态

# nginx 自带
sudo nginx -t                   # ⭐ 改完配置先测语法
nginx -v                        # 看版本

# 看日志（排查问题）
tail -f /var/log/nginx/access.log    # 实时看访问记录
sudo tail -n 50 /var/log/nginx/error.log   # 看最后 50 行报错
```

### 11.7 常见坑速查

| 现象 | 原因 | 解决 |
|------|------|------|
| `No package nginx available` | 没装 EPEL 源 | 回到 11.3 第 1 步装 `epel-release` 并修归档源 |
| `yum` 报 `mirrorlist.centos.org` 无法解析 | CentOS base 源失效 | 先做 7.1.0 换源 |
| 改了配置没生效 | 没 reload，或 `-t` 有语法错没加载 | `nginx -t` 看结果 → `systemctl reload nginx` |
| `nginx -t` 报 `syntax is invalid` / `unexpected "}"` | 配置少分号、少大括号 | Nginx 每条指令结尾要 `;`，按报错行号回去改 |
| 本机 `curl localhost` 通，Windows 浏览器打不开 | 防火墙 / 云安全组没放行 80 | 学习机关 firewalld；云服务器还要在控制台安全组放行 80 |
| Windows 浏览器访问 `localhost` 打不开 | localhost 指的是你 Windows 自己，不是虚拟机 | 地址栏填**虚拟机 IP**，用 `ip addr` 查 |
| 启动报 `Address already in use` / `bind() to 0.0.0.0:80 failed` | 80 端口被别的程序占用 | `sudo ss -lntp \| grep :80` 找占用者，停掉或改 `listen` 端口 |
| 页面还是旧的欢迎页 | 浏览器缓存 | Ctrl+F5 强制刷新，或换 test.html 这种新文件名测试 |

## 12. Redis 安装配置（必会）
> 🏷️ ⭐ 开发必会 —— Redis 是后端开发最常用的内存数据库（缓存 / 验证码 / 排行榜 / 分布式锁），这一节把它装上、跑通、学会用客户端连接和设密码

### 12.1 Redis 是干嘛的（先知道为什么装）

Redis 是一个**存放在内存里的键值（key-value）数据库**，读写极快（毫秒级、可达每秒十几万次），常被用来给 MySQL "减负"：

| 用途 | 例子 |
|------|------|
| **缓存**（最常见） | 把热点数据（首页商品、用户信息）从 MySQL 查一次后放进 Redis，下次直接读内存 |
| **验证码 / 登录态** | 短信验证码存 5 分钟、Token、Session |
| **计数器 / 排行榜** | 文章阅读量 `incr`、游戏积分榜 `zset` |
| **分布式锁 / 消息队列** | 多实例抢锁、简单队列（进阶） |

> 和 MySQL 的区别一句话：**MySQL 把数据存在硬盘（持久、慢一点），Redis 把数据放在内存（快、默认重启可能丢，可开持久化）**。两者是配合关系，不是替代。

### 12.2 安装方式怎么选（先选对方法）

CentOS 7 装 Redis 常见 2 种，**本课件主线用方法一（YUM + EPEL）**：

| 方式 | 版本 | 优点 | 缺点 | 推荐度 |
|------|------|------|------|--------|
| **方法一：YUM + EPEL 源** | 3.2.12 | 一条命令、自动配好 systemd、好卸载 | 版本较旧（但学习常用命令完全够） | ⭐⭐⭐⭐⭐ 学习首选 |
| **方法二：Remi 源** | 6.x / 7.x | 版本新、有 Stream 等新特性 | 要额外装 Remi 源（一步搞定），国内下载慢 | ⭐⭐ 项目确实要新版时 |

> ⚠️ **关键前提**：和 Nginx 一样，Redis 也**在 EPEL 扩展源里**，不在官方 base 源。直接 `yum install redis` 报 `No package redis available` 就是没装 EPEL。装 Nginx（11.3）时如果已经装过 EPEL 并修过归档源，**直接跳到第 2 步**。

### 12.3 方法一：YUM + EPEL 源（推荐，本课件主线）

#### 第 0 步：确认 CentOS base 源已修好

`yum install` 若还报 `Could not resolve host: mirrorlist.centos.org`，先回去做 **7.1.0 换源**。能 `yum repolist` 正常看到 base/updates/extras 再继续。

#### 第 1 步：装 EPEL 扩展源（已装过就跳过）

```bash
# 先写好 epel.repo 指向阿里云 epel-archive（先于装包，避免坏 epel.repo 让 yum 整体报错）
# ⚠️ 必须用 sudo tee，不能用 sudo cat >（sudo 不作用于重定向 >，会报"权限不够"）
sudo tee /etc/yum.repos.d/epel.repo > /dev/null << 'EOF'
[epel]
name=EPEL 7 - $basearch
baseurl=https://mirrors.aliyun.com/epel-archive/7/$basearch/
enabled=1
gpgcheck=0
EOF
sudo yum clean all && sudo yum makecache

# 再确认/补装 epel-release（已装会提示 already installed）
rpm -q epel-release || sudo yum install -y epel-release
sudo yum repolist          # 能看到 epel 一行 = 成功
```

> 如果报 **`Cannot find a valid baseurl for repo: epel`**，就是坏的 epel.repo 还没被覆盖，照上面顺序重做即可（详见 7.1）。

#### 第 2 步：安装 Redis

```bash
sudo yum install -y redis
```

看到 `Complete!` 即成功。验证：

```bash
redis-server --version     # Redis server v=3.2.12 ...（EPEL 提供的版本）
rpm -qa | grep redis       # redis-3.2.x 包存在 = 装上了
which redis-server         # /usr/sbin/redis-server
which redis-cli            # /usr/bin/redis-cli（客户端连接工具）
```

#### 第 3 步：启动 + 开机自启

```bash
sudo systemctl enable --now redis
```

> Redis 的服务名就是 **`redis`**（不是 redis-server，也不带 d），用 5.1 那套 systemctl 管理。

#### 第 4 步：验证（最关键，看到 PONG 才算成功）

```bash
# ① 看服务状态：Active: active (running)
systemctl status redis

# ② 用自带客户端 redis-cli 连上去做一次"心跳测试"
redis-cli ping
# PONG          ← 返回 PONG = Redis 正常运行，安装成功 ✅

# ③ 实际读写一条数据感受一下
redis-cli
127.0.0.1:6379> set name "zhangsan"     # 写入一个 key
OK
127.0.0.1:6379> get name                # 读出来
"zhangsan"
127.0.0.1:6379> exit                    # 退出客户端
```

> `redis-cli` 是 Redis 的命令行客户端：`redis-cli` 进入交互界面，`redis-cli 命令` 直接执行单条（如 `redis-cli ping`、`redis-cli get name`）。

#### 第 5 步：卸载 Redis（需要时用）

```bash
# 1. 停止服务 + 取消开机自启
sudo systemctl stop redis
sudo systemctl disable redis

# 2. 卸载软件包
sudo yum remove -y redis

# 3. 清理残留（配置、数据、日志）
sudo rm -rf /etc/redis.conf            # 配置文件
sudo rm -rf /etc/redis.d               # 配置目录
sudo rm -rf /var/lib/redis             # 数据目录（内存数据持久化的 rdb/aof 文件）
sudo rm -rf /var/log/redis             # 日志目录

# 4. 验证是否删干净
which redis-server                     # 应该: no redis-server in (...)
which redis-cli                        # 应该: no redis-cli in (...)
rpm -qa | grep redis                   # 应该没有输出
sudo ss -tlnp | grep :6379             # 6379 端口应该没人占用
```

### 12.3-B 方法二：Remi 源（想要新版 Redis 6/7 时用）

> EPEL 的 Redis 是 3.2.12（2017 年的版本），如果你需要 Stream、ACL、Redis Cluster 等新特性，走 Remi 源。Remi 是 CentOS/RHEL 上最流行的第三方软件源，专门提供新版软件包。

#### 第 1 步：装 Remi 源

```bash
# Remi 依赖 EPEL，所以 EPEL 源必须先装好（不管用方法一还是方法二，EPEL 都是基础）
sudo yum install -y https://rpms.remirepo.net/enterprise/remi-release-7.rpm
sudo yum clean all && sudo yum makecache
```

#### 第 2 步：启用 Redis 7 模块 + 安装

```bash
# 启用 remi 源里的 redis-7.0 模块（想装 6.0 就写 redis-6.0）
sudo yum-config-manager --enable remi-php74 remi-redis7.0

# 装完确认：redis-server --version 应该显示 Redis 7.x
sudo yum install -y redis
```

> ⚠️ Remi 源走 `rpms.remirepo.net`，国内服务器可能下载慢/超时。卡太久就换方法一（EPEL 走阿里云镜像秒开）。学习阶段 3.2.12 的常用命令（set/get/hash/list/pub/sub）和 7.x 完全一样，只是少了新特性。

#### 第 3 步：启动 + 验证

和方法一完全一样：

```bash
sudo systemctl enable --now redis
redis-cli ping                # 看到 PONG = 成功
```

**以下 12.4～12.7 节是两种方法共用的**（不管哪种方式装的，systemctl 命令、改配置流程全一样；但**配置文件路径略有差异**，见 12.4 表注）。

### 12.4 关键路径与配置（yum/EPEL 版，和编译安装不同）

| 用途 | 路径 | 说明 |
|------|------|------|
| **⭐ 主配置文件** | `/etc/redis.conf` | EPEL 版是**单文件**（注意：不是 `/etc/redis/redis.conf`） |
| 数据存放目录 | `/var/lib/redis/` | RDB/AOF 持久化文件（dump.rdb）放这 |
| 日志文件 | `/var/log/redis/redis.log` | 起不来 / 报错先看它 |
| 服务端程序 | `/usr/sbin/redis-server` | — |
| 客户端工具 | `/usr/bin/redis-cli` | 连接、操作 Redis 用 |
| 默认端口 | **6379** | Redis 标志性端口 |

### 12.5 改配置的正确流程（必会）

和 Nginx 一样有固定套路，**改的是 `/etc/redis.conf`，改完要重启服务**（Redis 改配置后用 restart，不是 reload）：

```bash
# ① 改配置
sudo vi /etc/redis.conf

# ② 重启服务让配置生效
sudo systemctl restart redis

# ③ 验证状态 + 连通
systemctl status redis
redis-cli ping          # PONG
```

#### 开发最常改的 3 个配置

打开 `/etc/redis.conf`，找到下面几行（用 `/关键词` 在 vi 里搜索）：

```conf
# ① 绑定地址：默认只允许本机连接（安全）
bind 127.0.0.1
#   学习时想让 Windows/其他机器连：改成 bind 0.0.0.0（监听所有网卡）

# ② 保护模式：默认开启。没设密码且 bind 放开时，只允许本机访问
protected-mode yes
#   对外放开 bind 后，要么设密码（推荐），要么学习时改成 no

# ③ 访问密码：默认无密码，注释状态
# requirepass foobared
#   去掉注释并改成自己的密码，例如：
requirepass 123456

# ④ 端口（一般不动）
port 6379
```

**设密码后怎么连接：**

```bash
redis-cli                          # 先进客户端
127.0.0.1:6379> get name          # 没认证直接操作会被拒
(error) NOAUTH Authentication required.
127.0.0.1:6379> auth 123456       # 输入密码认证
OK
127.0.0.1:6379> get name
"zhangsan"

# 也可以登录时直接带密码（-a）
redis-cli -a 123456 ping           # PONG
```

#### 让 Windows / 其他机器能连（学习环境）

需要**三件事都做**，缺一不可（和之前 MySQL 远程访问、Nginx 外网访问一个道理）：

```bash
# ① 改配置放开监听 + 关保护模式（或设密码），然后重启
sudo vi /etc/redis.conf
#   bind 0.0.0.0
#   protected-mode no        （学习环境；生产应设密码而不是关保护）
sudo systemctl restart redis

# ② 防火墙放行 6379（学习机也可直接按 5.4 关掉防火墙）
sudo firewall-cmd --permanent --add-port=6379/tcp
sudo firewall-cmd --reload

# ③ 用 Windows 上的 Redis 客户端（如 RedisDesktopManager / Another Redis Desktop Manager）
#    填 虚拟机IP:6379 连接
```

### 12.6 常用命令速查

```bash
# 服务管理（systemctl 一套，服务名 redis）
sudo systemctl start redis       # 启动
sudo systemctl stop redis        # 停止
sudo systemctl restart redis     # ⭐ 改完 redis.conf 后重启
systemctl status redis           # 看状态
sudo systemctl enable redis      # 开机自启（enable --now 已做过就不用重复）

# 客户端操作
redis-cli                        # 进入交互式客户端
redis-cli ping                   # 测连通，返回 PONG
redis-cli -a 密码 ping            # 带密码连接
redis-cli shutdown               # 从客户端关闭 Redis（一般用 systemctl stop）

# 看 Redis 是否在监听 6379
sudo ss -lntp | grep 6379
```

### 12.7 常见坑速查

| 现象 | 原因 | 解决 |
|------|------|------|
| `No package redis available` | 没装 EPEL 源 | 回 12.3 第 1 步装 `epel-release` 并修归档源 |
| `yum` 报 mirrorlist.centos.org 无法解析 | base 源失效 | 先做 7.1.0 换源 |
| `redis-cli ping` 报 `Could not connect` | 服务没启动 | `sudo systemctl start redis` 再看 status |
| `(error) NOAUTH Authentication required` | 设了密码但没认证 | 进客户端后 `auth 你的密码`，或 `redis-cli -a 密码` |
| Windows 客户端连不上 | bind 没放开 / 防火墙没放行 / 保护模式 | 按 12.5"让其他机器能连"三步逐一排查 |
| 改了配置不生效 | 没重启服务 | `sudo systemctl restart redis`（Redis 靠 restart 不是 reload） |
| 起不来，日志报错 | 配置写错（如少空格、密码非法字符） | `tail -n 50 /var/log/redis/redis.log` 看行号，改回后重启 |
| 找不到 `/etc/redis/redis.conf` | 装法不同路径不同 | **EPEL 版是 `/etc/redis.conf` 单文件**；源码编译才是 `/etc/redis/redis.conf` |

> 🔒 **生产安全提醒**：绝不要在生产把 Redis 直接 `bind 0.0.0.0` + `protected-mode no` + 无密码暴露公网——历史上大量 Redis 因此被扫描到、写入勒索数据。生产应：**设强密码（requirepass）、只监听内网 IP、防火墙限制来源、必要时开认证 ACL**。个人虚拟机学习可以放开，上线必须收紧。
